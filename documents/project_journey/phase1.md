# Local Friday 기획 및 문서 설계

## 1. 프로젝트 개요

Local Friday는 **오프라인 우선 개인 AI 비서 앱** 프로젝트다.  
영화 속 JARVIS / FRIDAY 같은 경험을 참고하되, 실제 구현 가능성을 우선하여 다음 목표로 설계했다.

- Android 스마트폰에서 로컬 실행
- 개인정보를 외부 API로 보내지 않는 구조
- Gemma 4 E4B-it 기반 MVP
- 텍스트 / 음성 / 이미지 입력 지원
- 캘린더 조회 및 일정 초안 생성
- 향후 Windows + 상위 모델 확장 가능

핵심 방향은 “전능한 AI”가 아니라,  
**오프라인 우선 + 승인 기반 + 개인용 비서**다.

---

## 2. 출발점: 기본 아이디어

처음 아이디어는 다음 질문에서 시작되었다.

> 아이언맨의 JARVIS, FRIDAY 같은 AI 시스템을 현실적으로 만들 수 있을까?  
> 그리고 AI Agent, AI Harness, LLM 구조를 활용해 개인 비서 형태로 구현할 수 있을까?

이에 따라 먼저 다음 내용을 정리했다.

- JARVIS / FRIDAY의 역할 분석
- AI Agent 개념
- AI Harness 개념
- LLM 기반 현실적 구현 방향

이 단계에서 내린 핵심 결론은 다음과 같다.

- 영화 속 AI는 단일 모델이 아니라 **여러 계층의 시스템**
- 현실 구현은 **Copilot → Agent → Semi-autonomous** 순서가 적절
- “전능한 자비스”보다 **도메인 특화 프라이데이형 비서**가 현실적
- 핵심은 모델 자체보다 **오케스트레이션, 메모리, 정책, 승인 구조**

## 3. 초기 구현 방향 논의

이후 사용 환경을 구체화하면서 프로젝트 방향이 더 명확해졌다.

### 사용자 요구 요약
- 개인 비서 형태
- 평소에는 네트워크 없이 로컬 실행
- Android Samsung 스마트폰 우선
- APK 형태의 MVP 구현 희망
- 추후 Windows 데스크톱 지원
- 모델 교체 가능 구조 필요
- 필요한 경우에만 검색 허용
- 메모리 데이터를 모바일↔데스크톱으로 이어서 사용 가능해야 함

초기에는 Gemma 3n 계열도 검토했지만, 이후 기준 모델을 **Gemma 4 E4B-it**로 정리했다.

## 4. 모델 및 실행환경 관련 핵심 의사결정

사용자가 아래와 같이 구체적인 기준을 제시했다.

### 사용자 입력 요약
- 모바일: Gemma 4 E4B-it
- 데스크톱: Gemma 4 26B-A4B
- 기기: Galaxy S25 Ultra
- APK 구현 방식은 C → B → A
  - C: sideload + 모델 수동 배치
  - B: 앱과 모델 분리 설치
  - A: 앱 내부/자동 다운로드
- 시스템 전체 무제한 제어는 목표 아님
- 권한 안에서 가능한 많은 것을 해보는 방향
- 영상은 이미지/오디오 파이프라인으로 분리
- 검색은 기본 OFF, 필요 시만 ON

### 이 단계에서 정리된 방향
- 모바일 MVP 기본 모델은 Gemma 4 E4B-it
- Windows 심화 처리용 모델은 Gemma 4 26B-A4B
- 검색은 질문 단위 옵션으로 설계
- 메모리는 파일/DB 구조를 분리해 향후 동기화 가능하게 설계
- Android SDK / Samsung SDK는 “OS 전권 제어”가 아니라 **권한 기반 도구 에이전트** 구조로 사용

## 5. 아키텍처 설계 단계

이후 프로젝트를 실제 구현 가능하도록 아키텍처와 패키지 구조로 나누었다.

### 핵심 구조
- UI Layer
- Assistant Core
- Model Runtime
- Agent Layer
- Harness / Policy Layer
- Memory Layer
- Platform Connector Layer

### 주요 설계 원칙
- UI와 AI 코어 분리
- ModelRunner 인터페이스 도입
- Agent와 Tool 분리
- 읽기 자동 / 쓰기 승인
- 오프라인 우선
- 메모리 5계층 분리
  - Profile
  - Conversation
  - Task
  - Knowledge
  - Audit

이때 실제 Android 패키지 구조와 파일 역할표, 그리고 초기 Todo/Task breakdown까지 정리했다.

## 6. 화면 설계 단계

그 다음 단계에서는 실제 사용성을 위해 UI/UX 설계를 진행했다.

### 디자인 기준
- 메인 컬러: 하늘색 `#5bc2e7`
- 톤앤매너: 차분하고 신뢰감 있는 실무형 비서 UI
- 하단 탭
  - 채팅
  - 일정
  - 메모리
  - 설정
- 우하단 FAB
  - 음성 입력

### 주요 UX 원칙
- 채팅은 단순 말풍선이 아니라 카드형 응답 지원
- 검색은 “이번 질문만”이라는 점이 UI에 드러나야 함
- 승인 작업은 Bottom Sheet로 처리
- 상태 표시(오프라인 / 모델 / 검색 여부)를 항상 명확하게 노출

이 단계에서 화면 설계서를 통해 버튼 위치, 탭 구조, 전환 애니메이션까지 정의했다.

## 7. 문서 산출물 1차 작성

프로젝트를 문서로 정리하면서 다음 4개 산출물을 만들었다.

1. 앱 설계서
2. MVP PRD
3. dev_breakdown
4. plan

각 문서는 처음에는 각각 독립적으로 작성되었고, 초기 단계에서 다음과 같은 역할을 가졌다.

- 앱 설계서: 구조와 시스템 설명
- MVP PRD: 제품 범위와 기능 정의
- dev_breakdown: 개발 작업 분해
- plan: 실행 계획

하지만 이후 검토 과정에서 문서 간 중복과 충돌이 발견되었다.

---

## 8. 1차 문서의 문제점 정리

문서가 쌓이면서 다음 이슈가 드러났다.

### 1) 문서 간 역할 중복
- 설계서에도 개발 우선순위가 들어감
- dev_breakdown에도 제품 범위 설명이 들어감
- plan에 디렉토리 구조와 작업 분해가 같이 있음

### 2) MVP 범위 충돌
예를 들어:
- PRD에서는 검색 / export-import / 공유 인텐트가 MVP 포함처럼 보임
- 앱 설계서에서는 일부를 v1로 둠

### 3) 용어 혼용
- Local Friday / Friday 혼용
- SearchAgent / SearchGateway / WebSearchGateway 혼용
- AuditLogger / AuditTrailService / Audit Memory 표현 혼용

### 4) 운영 요소 부족
- 테스트 전략
- 롤백 전략
- 운영 계획
- 문서 간 우선순위 규칙

이 문제를 해결하기 위해 문서 체계를 다시 설계했다.

## 9. 문서 체계 재정비(v2)

문서를 실제 팀 개발용으로 바꾸기 위해 아래 기준으로 역할을 다시 정의했다.

**목적:** 작업 기준서  
내용:

- 태스크
- 의존성
- 병렬 개발 가능 여부
- DoD

### 4. plan
**목적:** 실행 계획서  
내용:
- 실제 일정 흐름
- 역할 분담
- 마일스톤
- 운영 계획
- 롤백 계획

## 10. v2 문서에서 정리된 핵심 결정

문서 재정비 과정에서 가장 중요한 결정은 다음과 같다.

### 명칭 통일
- 프로젝트명: **Local Friday**
- 앱 표시명: **Friday**

### MVP 범위 정리
MVP 포함:
- 텍스트 채팅
- push-to-talk 음성 입력
- 이미지 입력(스크린샷/문서)
- 캘린더 조회
- 일정 초안 생성 + 승인 저장
- Conversation/Profile memory
- 기본 설정 화면
- 기본 Audit logging

v1로 이동:
- 질문 단위 검색
- export/import
- 공유 인텐트
- Task/Knowledge/Audit memory 확장 UI

### 이유
이렇게 해야 개발 범위가 과도하게 커지지 않고, 실제 구현과 검증이 가능한 MVP가 된다.

## 12. 주요 프롬프트와 응답 흐름 요약

전체 대화는 아래 5단계로 요약할 수 있다.

### 1) 개념 정의 단계
사용자는 JARVIS / FRIDAY, AI Agent, AI Harness, LLM 기반 구현 가능성을 질문했다.  
이에 대해 영화 속 AI를 현실 시스템 관점으로 해석하고, Agent / Harness / 멀티모달 / 오케스트레이션 구조를 정리했다.

### 2) 구현 방향 구체화 단계
사용자는 로컬 우선, Android Samsung 스마트폰, APK, 모델 교체, 데스크톱 확장, 선택적 검색, 메모리 연속 사용 요구를 제시했다.  
이에 따라 오프라인 우선 개인 비서라는 제품 방향과 모바일/데스크톱 역할 분리를 정리했다.

### 3) 기술 선택 및 구조 설계 단계
사용자는 Gemma 4 E4B-it / 26B-A4B, S25 Ultra, 검색 OFF 기본, 권한 기반 액션, 영상 분해 처리 방향을 확정했다.  
이에 맞춰 아키텍처, 패키지 구조, 메모리 구조, UI/UX 방향, 개발 우선순위를 설계했다.

### 4) 문서화 단계
이후 PRD, 앱 설계서, dev_breakdown, plan 문서를 순차적으로 작성하고 PDF/MD 파일로 정리했다.  
이 과정에서 MVP 범위, 메모리 구조, Android 아키텍처, 화면 설계, 작업 분해가 문서화되었다.

### 5) 문서 재정비 단계
마지막으로 4개 문서 간 충돌과 중복을 분석하고, 문서 목적별 역할을 다시 정의했다.  
그 결과, 실제 팀이 바로 개발을 시작할 수 있는 수준의 v2 문서 체계를 완성했다.

## 14. 정리

이 프로젝트는 단순히 “AI 비서 앱을 만든다”는 아이디어에서 시작했지만, 여러 차례의 질문과 답변, 범위 조정, 구조 재설계를 거치면서 최종적으로 **실제 개발 착수가 가능한 문서 체계**까지 정리되었다.

중요한 점은 다음이다.

- 처음부터 완전한 자비스를 만들려 하지 않았다.
- 로컬 실행, 보안, 승인, 구조 분리를 우선했다.
- 문서도 하나의 설계 산출물로 보고, 반복적으로 다듬었다.
- 최종적으로 제품/설계/개발/계획 문서를 분리해 팀 단위 협업이 가능한 상태로 만들었다.
