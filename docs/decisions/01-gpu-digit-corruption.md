# 긴 대화에서 숫자가 깨지던 문제 — GPU FP16 정밀도

> 원문: [ADR-016](../architecture.md) 「미확정 — 글자 유실」, ADR-020, **ADR-021**(원인 확정), **ADR-029**(최종 처방) · 실험 exp15·exp22·exp27~exp31·exp51
> 기간: 2026-08-12 발견 → 08-13 원인 확정·1차 처방 → 10-14 최종 처방(0.37.0)

## 한 문장
실기기의 긴 대화에서만 일정 시각·숫자가 깨지는 문제를, 실기기 대화 기록을 PC 실험 환경으로 옮겨 결정적으로 재현하고, 가설 다섯 개를 하나씩 기각한 끝에
**GPU 텍스트 디코더의 FP16 활성화 정밀도 × 문맥 깊이**로 원인을 확정했다. 처음에는 대화 예산을 발병점(약 1,850토큰) 아래인 1,700으로 묶어 막았고,
런타임이 FP32 설정을 열어 준 뒤에는 FP32로 바꿔 예산을 2,500으로 되돌렸다. 두 단계 모두 단위 테스트가 예산 불변식을 지킨다.

## 1. 증상 (2026-08-12, Galaxy S25 Ultra, 앱 0.11.1)
- "다음주 월요일 10시 팀 회의" → 일정 승인 카드에 `202026-081717T010000`.
- 앱 DB 에서 `2026-08-17T10:00` → `2026-08-17T01:000`, `11월` → `111월`, 위키 답변에 "20202년".
- **짧은 대화에서는 정상, 이어지던 긴 대화에서만** 깨졌다. 일정 시각·비밀번호처럼 틀리면 안 되는 값이 대상이라 치명적이었다.

## 2. 의심했고 기각한 것
| 가설 | 어떻게 확인했나 | 결과 |
|---|---|---|
| 우리 코드(스트리밍 조립)가 글자를 흘린다 | 툴 인자는 네이티브가 파싱한 구조체에서 읽는데도 깨져 있었다. 인자 경로 전 구간 감사 — 값을 만지는 코드 없음 | 배제 (ADR-016·020) |
| 제약 디코딩(FST 문법)이 숫자를 망친다 | 같은 설정·짧은 문맥에서 두 번 모두 정확 (exp15) | 배제 |
| 런타임(AAR) 버전 문제 | 0.16.0 으로 올려 실기기에서 다시 — 같은 증상 | 기각 (ADR-020) |
| KV 용량(4,096)을 조용히 넘었다 | 턴마다 토큰 수 계측을 넣고 실기기 재현 — **2,783/4,096 에서 깨짐, 초과 경고 0건** | 기각 (ADR-021) |
| 앞의 깨진 답이 기록에 남아 모델이 따라 한다 | 실기기와 같은 깊이(2,784)의 오염된 기록을 **PC CPU** 로 — 온전 (exp27) | 기각 |

여기서 중요했던 것: **실기기 DB 를 실험 픽스처로 보관**해 두었기 때문에, 실기기와 거의 같은 대화를 PC 에서 몇 번이고 똑같이 돌릴 수 있었다
(생성은 greedy 라 결정적 — 같은 입력이면 같은 출력).

## 3. 원인 확정 (2026-08-13, exp28~exp30)
| 실험 | 조건 | 결과 | 의미 |
|---|---|---|---|
| exp28 | PC **GPU** × 같은 문맥 | 깨짐 (`20826-08-17T0100:000`) | GPU 에서 재현 확보 |
| exp29-D | PC GPU × **깨끗한** 깊은 문맥 | 깨짐 | 방아쇠는 오염이 아니라 **깊이** |
| exp29-E | PC GPU × 같은 문맥 + **FLOAT32 활성화** | 온전 | 원인 = **FP16 활성화 정밀도** |
| exp30 | PC GPU, 깊이 이등분 | **1,854 온전 / 2,122 깨짐** | 발병 경계 |

런타임 로그가 메커니즘을 확인해 줬다 — *"System's default activation type for Text decoder is fp16"*. 문맥이 깊어지면 FP16 의 수치 오차가 쌓여
greedy 의 숫자 토큰 선택이 뒤집힌다. CPU 는 온전, x86_64 PC GPU 에서도 재현 — 기기(ARM)의 문제가 아니었다.

## 4. 1차 처방 — 예산을 발병점 아래로 (0.15~0.16, ADR-021)
FP32 가 정답이었지만 **안드로이드 런타임(AAR 0.16.0)이 그 설정을 노출하지 않았다**(파이썬 패키지에만 있음 — 클래스를 전수 확인). 대안 비교:

| 후보 | 판정 |
|---|---|
| GPU 전용 모델 변형 | 같은 조건에서 온전했지만 **오디오·비전 인코더가 없다** — 음성·이미지 기능이 죽는다 → 기각 |
| CPU 로 전환 | 정확하지만 4B 모델 CPU 속도로는 채팅이 안 된다 → 기각 |
| **대화 예산을 발병점 아래로** | **채택**(사용자 결정) |

- 예산 3,000 → **1,700**. 1,700 은 바닥이다 — 고정 몫(시스템 지시·툴 선언, 당시 예약 1,400) + 최소 대화 기록 300. 이보다 낮추면 매 턴 대화 재설정 루프가 된다.
- 일반 턴의 생성 시점 깊이 ≈ 1,800 < 1,854(온전 실측선) — **일정 인자를 만드는 턴이 보호된다**.
- 같은 날 실기기 확정: 같은 문장의 승인 카드가 `2026-08-17 / 10:00–11:00` 으로 온전, 기기 캘린더에도 10:00 으로 저장.
- **정직한 한계**: 툴 결과를 받은 뒤의 턴은 깊이가 ~2,350 까지 올라 노출이 남았다 → 일정 인자는 ISO 형식 검증(BAD_FORMAT, 0.15.0)이 하류를 지킨다.
- **대가**: 대화 기록 2~3턴, 재설정이 잦아짐, **툴을 더 선언할 공간이 없음**(여유 50토큰).
- 상류(Google)에 PC 재현 케이스와 함께 FP32 설정 노출을 요청하는 보고 초안을 남겼다.

## 5. 최종 처방 — FP32 로 바꾸고 예산을 되돌림 (0.37.0, 2026-10-14, ADR-029)
런타임 0.18.0 의 `EngineConfig` 에 `activationDataType` 이 생겼다 — 릴리스 노트에는 없고 **클래스 파일 비교로 찾았다**.

| | FP16 (0.18) | **FP32 (0.18)** |
|---|---|---|
| PC GPU 발병 (exp51) | 2,028 온전 / 2,141 깨짐 | **3,682 까지 온전** |
| 기기 깊은 대화 | ~2,300 이후 `200026-10-19` | 2,486~2,966 **온전** |
| 툴 스모크 12건 + 이미지·오디오 | 12/12 | 12/12 |
| 생성 속도 | 11.1·10.8 t/s | 10.6·10.2 t/s (**−5%**) |
| 첫 응답(시스템 지시 읽기 포함) | 9.4·13.6 s | 17.0 s (**+4~5 s**) |
| 메모리(PSS) | 4.34 GB | 4.93~4.96 GB (**+0.6 GB**) |

- GPU 일 때 FP32, 대화 예산을 설정 범위 2,000~2,800(기본 2,500)으로. 상한 2,800 의 근거 둘: ① 툴 결과(최대 500)가 턴 중간에 들어와도 천장 3,328 이하
  ② 기기에서 FP32 온전을 확인한 깊이 2,966 이하.
- **대가**: 첫 응답 +4~5초, 메모리 +0.6GB, 속도 −5% — 숫자 정확성과 툴 공간을 얻고 낸 값.

## 6. 재발 방지
- `TokenBudgetInvariantTest` — "예산 상한이 GPU FP32 기기 실측 온전선 아래다", "예산 상한에 툴 결과를 얹어도 프리필 천장을 넘지 않는다",
  "재설정 하한이 재생성 루프를 만들지 않는다" 등 13개 불변식. 상수를 잘못 바꾸면 빌드 게이트에서 깨진다.
- `EngineConfigTest` — GPU 면 FP32, CPU 는 기본값.
- 기록용 상수 `GPU_DIGIT_ONSET_SAFE_TOKENS`(1,854) — FP16 으로 되돌릴 때 예산 상한이 다시 이 아래여야 한다.

## 면접 예상 질문
- **왜 처음부터 FP32 를 안 썼나?** — 안드로이드 런타임이 설정을 노출하지 않았다. 그래서 원인은 확정해 두고, 노출될 때까지 예산으로 막았다. 노출되자 바로 바꿨다.
- **1,700 은 어떻게 정했나?** — 발병점 실측(1,854 온전)보다 낮으면서, 고정 몫 + 최소 대화 기록이 성립하는 바닥. 감으로 정한 숫자가 아니다.
- **PC 실측이 기기에도 맞는다고 어떻게 아나?** — PC 는 가설을 가르는 곳이고, 최종 판정은 실기기 재검증으로 했다(같은 문장·같은 날 확인). PC 와 기기의 경계가 다를 수 있다는 한계도 기록했다.
- **지금도 1,700 인가?** — 아니다. FP32 전환 뒤 기본 2,500(2,000~2,800). 1,700 은 1차 처방이었다.
- **가장 어려웠던 점?** — 그럴듯한 가설(버전·용량 초과·오염 모방)이 연달아 있었다는 것. 계측을 넣어 하나씩 숫자로 기각했다.
