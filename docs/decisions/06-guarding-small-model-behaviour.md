# 프롬프트로 안 고쳐지는 모델 행동을 앱이 막기 — 메모 가드와 거절 기록

> 원문: CHANGELOG **0.38.6 ~ 0.38.9**, 계획서 `docs/plans/0.38.6~0.38.9` · 실험 exp56·exp61·exp62·exp64 · 시기: 2026-10-23 ~ 10-27

## 한 문장
4B 모델은 일부 행동을 프롬프트 문구로 고쳐도 다시 돌아왔다 — 되물었는데 메모를 저장하려 하고, 사실만 말했는데 저장하고, 앞에서 한 거절을 따라 했다.
이런 행동은 **앱이 판정해서 막고**(실행 전 가드, 모델 입력 기록 조정), 효과는 실험실과 실기기 양쪽으로 확인했다. 실험실은 통과했는데 실기기에서 실패한 경우도 있었고, 그 차이에서 원인을 찾았다.

## 원칙
- 먼저 프롬프트 후보를 실측한다. 후보가 모두 효과 없을 때만 코드로 막는다(토큰도 아끼고, 모델이 보는 것이 덜 복잡해진다).
- 막을 때는 **안전한 쪽으로 깨지게** 한다 — 판정이 틀려도 결과가 "한 번 더 묻기"나 "그대로 진행"이 되도록.

## 사례
| 증상 | 프롬프트로 해 본 것 | 앱이 한 것 | 결과 |
|---|---|---|---|
| 일정·메모 승인을 거절하면 거짓 성공, 앞 턴 답 따라 하기("추가해도 될까요?"), 지시문 읊기, 거절을 오류처럼 말하기 (0.38.6) | 결과 문구 다섯 판(exp38d·e, exp49, exp56) — 매번 넷 중 하나가 남음 | 거절이면 모델을 다시 부르지 않고 **고정 문장**("메모에는 남기지 않았어요.")으로 턴을 끝냄 | 모델이 답하지 않으니 그 행동이 생길 자리가 없음(실기기 T 절 확인) |
| "송장번호 다시 알려줘"(되묻기)에 메모 저장을 부름 (0.38.7) | 트리거 문구 다섯 판 2~3/6 | 되묻는 말(정규식)이면 저장 호출을 승인 시트 없이 막고 "그 값을 답하라"를 돌려줌(`RepeatRequest`) | 값을 답함 3/3 |
| 저장 부탁 없이 사실만 말해도 저장 (0.38.8 → 0.38.9) | 트리거 줄 수정: 새 대화 실험실에서 저장 호출 5 → 0/8 | — | **실기기에서는 3/3 저장** |
| 앞에서 거절한 기록이 있으면 일상 요청까지 "그런 기능은 없어요" (0.38.8 → 0.38.9) | 역할 줄·"요청마다 새로 판단"·턴 리마인더 — 모두 현행보다 낫지 않음 | 모델 입력 기록에서 거절 쌍을 뺌 | 6/12 → 1/12 |

## 실험실은 통과, 실기기는 실패 — 왜 (0.38.8 → 0.38.9)
- 사실만 말할 때 "메모해 둘까요?"라고 묻게 한 문구는 실험실에서 저장 호출 0/8 이었는데, 휴대폰에서는 3/3 저장 시트가 떴다.
- 차이는 **대화 상태**였다. 실험실은 새 대화로 쟀고, 휴대폰 기록에는 "사실 → 저장 시트 → 거절" 쌍이 쌓여 있었다. 같은 쌍을 실험실 기록에 넣자 재현됐다(exp62g):
  쌍 0개 1/7, 1개 2/7, 3개 **5/7**. 기록에 끌리는 행동은 문구로 이기기 어렵다.
- 그래서 앱이 막았다(`MemoSaveIntent`): 사용자 말에 저장 낱말(기억해·저장·메모·까먹·알아둬 …)이 없고 바로 앞 비서 말이 저장 물음도 아니면, 저장 호출을 막고
  "먼저 '메모해 둘까요?'라고 물으라"를 돌려준다. 결과 문구 세 후보를 재서 하나를 골랐다(exp64b: 막힌 뒤 물어봄 6/7).
- 낱말 목록을 처음 그대로 쓰면 "이거 알아둬", "까먹으면 안 돼" 같은 정상 부탁 5건이 막힌다는 것을 미리 재서(exp64) 목록을 넓혔다 — 부작용을 사용자에게 먼저 설명하고 결정받았다.
- 실험 중 새 결함이 하나 더 보였다 — "메모해 둘까요?" 뒤 "응"이라 했는데 모델이 저장을 부르지 않고 "메모해 두었어요"라고만 함(2/6). 이 경우 **앱이 저장 시트를 직접** 연다.
- 실기기 재확인: 사실만 말하기 → 물음, "응" → 시트 → 메모 저장, 목록 밖 부탁 → 바로 시트.

## 고친 것이 만든 문제도 고쳤다
- 거절을 기록에서 빼자 "왜 안 된다고 했어?"에 **12/12 "기억이 나지 않아요"** 가 됐다(exp64d) — 모델이 자기 거절을 모르게 됐다.
- 사용자가 거절을 되묻는 말("왜 안", "안 된다고")일 때만 그 턴에 거절을 기록에 남기도록 바꿨다 → 12/12 거절한 주제와 이유를 답함. 다음 턴부터는 다시 뺀다.

## 대가와 한계
- 장치가 늘수록 서로의 상호작용·오탐을 재야 한다. 정규식은 말투·음성 전사 오타에 약하다.
- 기록을 고치거나 답을 고친 턴 뒤에는 엔진의 대화를 다시 만든다 — 실기기에서 다음 질문이 **6~7초** 늦었다(0.39.0 M1).
  0.39.2 에서 이 비용을 **답을 읽는 동안** 치르게 바꿨다 — 승인 거절 뒤 다음 질문 6.9초 → 0.66초(ADR-030).
- 장치끼리 겹쳤다 — 거절 판정이 "진단은 해 드릴 수 없지만, 물을 …"처럼 **도운 답까지** 기록에서 빼, 다음 턴이 그 내용을 몰랐다(3건 중 2건). 겹침을 재는 회귀 세트로 찾아 좁혔다(0.39.2 M2).
- 장치 목록·오탐 방향·비용은 ADR-030 한 표에 모았고, 실기기 대화 모양을 넣은 **고정 회귀 세트**를 회차마다 돌린다(0.39.0~).

## 면접 예상 질문
- **왜 프롬프트로 안 고치고 코드로 막나?** — 먼저 프롬프트 후보를 쟀고, 효과가 없을 때만 막았다. 작은 모델은 기록의 패턴에 끌리는 행동이 문구보다 강했다.
- **실험실을 믿을 수 있나?** — 믿을 수 있는 범위가 있다. 새 대화로 잰 실험실이 실기기의 쌓인 기록을 재현하지 못한 사례가 있었고, 그 차이를 재현해 원인을 찾았다. 그래서 실기기 확인이 각 회차의 마지막 단계다.
- **규칙이 계속 늘면?** — 가장 큰 기술 부채였다. 0.39.2 에서 목록(ADR-030)·겹침 회귀 세트·`BaseAgent` 단계 분리(실행 전 가드 / 답 후처리)를 했고,
  장치를 하나 더할 때는 표에 한 줄과 회귀 문항을 함께 넣는다. 다음 정리는 토큰 예산(0.39.3) — 장치가 쓰는 토큰도 같은 표로 본다.
