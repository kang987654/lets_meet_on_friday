# 임베딩 없이 기억 찾기 — 매 턴 자동 주입을 버리고 검색 툴과 2글자 묶음 점수로

> 원문: **ADR-013**(자동 주입 → 검색 툴), ADR-022(에피소드 기억), **ADR-025**(바이그램 스코어러), ADR-026(임베더 제거) · 실험 exp33·exp37
> 시기: 2026-08-07 ~ 09-03

## 한 문장
앱은 매 턴 질문을 임베딩해 비슷한 메모 3건을 프롬프트에 붙이고 있었는데, 재 보니 그 임베더의 **한국어 분별력이 0**이라 사실상 무작위 메모를 붙이고 있었다.
자동 주입을 걷어 내고 모델이 필요할 때 부르는 **검색 툴**로 바꿨고, 검색은 한국어 조사에 강한 **2글자 묶음(바이그램) 점수**로 했다. 임베더는 지웠다(APK −28MB).

## 1. 발견 — 임베더가 한국어에서 상수였다 (ADR-013)
앱에 실린 MediaPipe 문장 임베더를 PC 에서 같은 설정으로 재 봤다.

| | 관련 문장 쌍 | 무관 문장 쌍 | 분리도 |
|---|---|---|---|
| 영어(대조군) | 0.842 | 0.587 | **+0.255** |
| 한국어 | 0.973 | 0.972 | **+0.000** |

- "자전거 비밀번호는 1234" ↔ "내 자전거 비밀번호 뭐였지?" = 0.946, ↔ "트와이스 나연에 대해 알려줘" = **0.946**. 어떤 임계값으로도 가를 수 없다.
- 모델 파일 어휘를 열어 보니 한글은 1글자 토큰 16,079개, 2글자 이상 8개 — 한국어 서브워드가 학습돼 있지 않았다.
- 실제 검색: 메모 8건·질의 7건 top-1 **1/7**(무작위 기대 1/8). 어떤 질의든 같은 3건이 나왔다.
- 즉 기존 동작은 "관련 기억 찾기"가 아니라 **"무작위 메모 3건을 매 턴 질문 앞에 붙이기"** 였다 — 토큰을 쓰고 환각 재료를 주면서 회상은 안 됐다.

## 2. 결정 — 자동 주입 대신 검색 툴
- 모델이 필요할 때 `search_memory(키워드)` 를 부른다. 한국어 이해는 이미 온디바이스 LLM 이 하므로 **질의어 뽑기를 모델에게 맡기는 것**이 가장 싼 의미 검색이다
  (문장 전체 "내 자전거 비밀번호 뭐였지?"로는 0건, 모델이 뽑은 "자전거 비밀번호"로는 정확히 맞는다).
- 못 찾으면 오류가 아니라 "없습니다 / 추측하지 마세요"를 성공 결과로 돌려준다 — 오류로 주면 모델이 도구 실패로 보고 지어내는 쪽으로 기운다.
- 대화는 30분 쉬면 **에피소드**로 닫고 기기 안에서 제목·태그·요약을 만든다(ADR-022). 이 요약이 검색 대상이 되고, 태그(동의어 포함 5~8개)가 쓰기 시점의 의미 보강을 맡는다.

## 3. 검색 방식 — FTS5 가 아니라 인메모리 바이그램 (ADR-025)
- 한국어는 조사·어미가 붙어("회의를", "회의에서") 어절 단위가 불안정하다. 2글자 창은 "회의"를 보존한다. 3글자(FTS5 trigram)는 2글자 질의를 못 다룬다.
- FTS5 를 쓰지 않은 이유: Room 에 `@Fts5` 가 없고, 내장 토크나이저는 한글을 어절 단위로만 자르며, 기기 SQLite 의 가용성도 확인해야 한다. 개인 규모(문서 수백)에서 전수 스캔은
  2,001 문서 17ms(JVM). 그래서 **규모 게이트**를 적었다 — 문서 2,000건 초과 또는 스캔 50ms 초과가 실측되면 그때 FTS5 로.
- 정확한 일치(LIKE)를 먼저, 바이그램은 정렬 기준과 "0건일 때 2차 통로"로. 2차 통로에는 최소 겹침 0.5 — 없으면 관계없는 문서까지 끌어와 "없다"고 해야 할 자리에 잡음을 낸다.
- 드로어(사람이 쓰는 검색)와 툴(모델이 쓰는 검색)을 같은 점수로 통일 — "비서는 못 찾는데 나는 보이는" 불신을 막는다.

## 4. 성적 — 그리고 실험 조건의 함정
| 조건 | 결과 |
|---|---|
| exp33 — 질의에 **사용자 원 질문 전체**를 넣음 | recall@1 **16/16** |
| exp37 — **실제 앱 프롬프트**에서 모델이 뽑은 키워드로 | 현행 11 · 바이그램 11 · 항상 원 질문으로 확장 13 · 0건일 때만 확장 11 (/16) |

- 같은 검색기인데 결과가 달랐다. 차이는 검색기가 아니라 **질의 조건** — 원 질문을 통째로 넣던 실험이 앱 조건을 과대평가했다.
- 놓친 것의 실체는 "0건"이 아니라 **적중 중 순위 오답**(키워드가 넓어 비슷한 문서 중 오답)과 **툴 미호출**이었다. 그래서 "0건일 때만 확장"은 이득이 0.
- "항상 확장"(13/16)은 검색마다 +1~2초 — 2문항을 위해 모든 검색을 늦추지 않기로 하고 측정된 상한으로 남겼다.

## 5. 대가와 다음
- 진짜 의미 검색은 없다 — "내가 좋아하는 음료가 뭐지?" ↔ "커피보다 녹차를 선호함"처럼 겹치는 글자가 없는 질의는 태그·모델 키워드에 기댄다.
- 다음 순서(로드맵 0.39.5): 놓치는 질의 세트로 실측 → 태그에 상위 개념 → 질의 확장 → 그래도 부족하면 **한국어를 실제로 구분하는** 임베더를 새 ADR 과 같은 세트 A/B 로.
  임베더 자리(인터페이스·DB 컬럼)는 그때를 위해 남겨 두었다(ADR-026).

## 면접 예상 질문
- **왜 벡터 검색을 안 썼나?** — 썼다가 재 보니 한국어 분별력이 0 이었다. 한국어 임베더를 넣기 전에, 이미 한국어를 아는 LLM 에게 키워드를 뽑게 하는 쪽이 싸고 측정 가능했다.
- **16/16 인데 왜 11/16 이라고 하나?** — 실험 조건과 앱 조건이 달랐다. 앱 조건으로 다시 잰 숫자가 진짜다.
- **규모가 커지면?** — 게이트를 숫자로 적어 두었다(2,000건 또는 50ms). 넘으면 FTS5 + 앱 측 바이그램 컬럼.
