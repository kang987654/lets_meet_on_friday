> **상태**: 승인 (2026-10-01)

# 수동 기억 정리 2차 — 에피소드 중복 통합 (0.31.0)

## Context

0.30.0 1차(주간 회고 + 지식 노트 병합)에 이어, **같은 주제가 30분 무활동 경계로 끊겨 여러 에피소드로 갈라진 것**을 합친다.
드로어 아카이브에 "치과 예약 일정 추가" / "일정 및 알림 설정 요청"처럼 같은 일이 조각나 보이고, 검색 회수도 조각 단위로 나뉜다.

**1차와 다른 점 (실험으로 아직 확인되지 않은 것)** — exp42 는 한 줄 사실 노트만 쟀다. 에피소드는 제목·태그 5~8개·여러 문장 요약이라
① "숫자 일치 + 본문 겹침" 가드가 그대로 맞는지 ② "같은 주제가 이어진 것인가" 판정 정확도 — 둘 다 **미측정**이다. M0 결과에 따라
범위가 줄 수 있다(예: 인접 에피소드만).

**현황 (탐색 확정)**:
- 메시지는 `conversation.episodeId` 로 에피소드에 귀속, 재배정 API `ConversationRepository.assignEpisode(messageId, episodeId)` 있음.
- 회수 칩: 답변 메시지의 `conversation.recallEpisodeIds`(TEXT 컬럼)에 에피소드 id 가 박혀 있다 — 통합으로 지운 에피소드를 가리키면
  칩 라벨이 비고 시트가 열리지 않는다. **id 재매핑 쿼리가 없다**(신설 필요).
- 요약: `SummarizeEpisodeUseCase`(exp33 검증 프롬프트, 입력은 `buildEpisodeTranscript` 토큰 캡). 통합 후 요약은 **이것을 재사용**해
  새 요약 프롬프트를 만들지 않는다.
- 자동 추출(C′2)은 스케줄러가 요약 직후 부른다 — 통합 재요약에서는 부르지 않는다(이미 추출된 사실의 중복 제안 방지).
- 잠금: `BackgroundInferenceGate`(0.30.0) — 정리 실행기와 자동 요약 드레인이 공유.

## 사용자 확정 결정
1. 1차와 같은 수동 정리 버튼의 다음 단계로 붙인다(새 버튼 없음) — 2026-10-01 "2차 구현" 지시.

## 승인 결정 (2026-10-01 — 전부 제안대로)
- **D1 후보 범위**: SUMMARIZED 에피소드 중 **시간상 인접한 쌍**(앞 에피소드 끝 ~ 뒤 에피소드 시작 ≤ 24시간)만(확정). 멀리 떨어진 같은
  주제(지난달과 이번 달 치과)는 합치지 않는다 — 시간 맥락이 다른 대화를 합치면 요약이 오히려 흐려진다.
- **D2 통합 방식**: 뒤 에피소드의 메시지를 앞 에피소드로 재배정 → 회수 칩 id 재매핑 → 뒤 에피소드 삭제 → 앞 에피소드 재요약(확정).
- **D3 확인 방식**: 1차와 같은 미리보기·**체크 기본 해제**(확정 — 제목 두 개 → "합친 뒤 다시 요약" 표시. 합친 요약은 적용 후에 생기므로
  미리보기에는 원래 제목·요약만).

## 고정 제약
- 채팅 프롬프트 무변경(oneShot 만) → `MEASURED_OVERHEAD` 무관. 판정 프롬프트는 M0 실측 원문 고정.
- 데이터 무결성: 재배정·재매핑·삭제는 **한 트랜잭션**(Room `@Transaction`) — 중간 실패로 메시지가 고아가 되지 않게.
- 재요약 실패 시 에피소드는 CLOSED 로 돌려 기존 catch-up 이 다시 요약하게 한다(데이터 손실 없음 — ADR-022 계약).
- 합성 데이터만 커밋. 기존 단언 수정 0건 목표.

## M0 — 실험실 실측 (exp44)
- 합성 에피소드 20개(제목·태그·요약): 같은 주제가 끊긴 쌍 6, 시간만 인접한 다른 주제 쌍 5(함정), 주제는 같지만 며칠 떨어진 쌍 3.
- (a) 후보 규칙: 인접(≤24h) × 제목+태그 바이그램 겹침 임계 — 재현율/후보 수.
- (b) 판정 프롬프트("두 대화가 같은 일이 이어진 것인가: 같음/다름") — 오병합(다른 주제 합침) 수가 게이트. 1차처럼 0 을 못 맞추면
  체크 기본 해제로 보완하되, **오병합이 2건 이상이면 범위를 줄이거나 회차 보류**를 사용자에게 다시 묻는다.
- (c) 통합 재요약: 두 대화를 이은 전사를 `SummarizeEpisodeUseCase` 프롬프트로 — 형식 준수·양쪽 주제 모두 반영 여부.

## M1 — 데이터
- `ConversationDao`: `UPDATE conversation SET episodeId = :to WHERE episodeId = :from`, 회수 칩 재매핑 — 저장 형식은 공백 없는
  쉼표 목록(`ConversationRepositoryImpl`: `joinToString(",")`)이라 **경계 일치 치환**: `',' || recallEpisodeIds || ','` 에서
  `,from,` → `,to,` 후 양끝 쉼표 제거(다른 id 의 부분 문자열을 건드리지 않게). 같은 행에 to 가 이미 있으면 중복이 생기므로 매퍼 읽기에서 distinct.
- `EpisodeRepository.mergeInto(from, to)` — 위 둘 + 원본 삭제를 `@Transaction` 으로. 마이그레이션 없음.
- 테스트: Room 인메모리(Robolectric) — 재배정·칩 재매핑(다른 id 의 부분 문자열을 건드리지 않음)·원본 삭제·실패 시 롤백.

## M2 — 도메인
- `PlanEpisodeMergeUseCase`: 후보(M0 규칙) → 판정 oneShot → 제안(`EpisodeMergeProposal(first, second)`).
- `ApplyEpisodeMergeUseCase`: `mergeInto` → 합친 메시지로 `SummarizeEpisodeUseCase` → 성공 시 SUMMARIZED 갱신, 실패 시 CLOSED.
- 테스트: 인접하지 않은 쌍은 모델에 안 감, 다름은 제안 없음, 재요약 실패 시 CLOSED, 감사 로그.

## M3 — 실행기·화면
- `MemoryCleanupRunner` 단계에 `EPISODE_MERGE` 추가(회고 → 노트 병합 → 에피소드 통합), Review 에 에피소드 제안 섹션, 적용 결과 문구.
- 테스트: 기존 `MemoryCleanupRunnerTest`/`MemoryCleanupScreenTest` 는 생성부만(새 유스케이스 인자), 신규로 에피소드 제안 체크·적용.
