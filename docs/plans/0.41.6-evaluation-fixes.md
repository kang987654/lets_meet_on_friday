# 0.41.6 — 외부 평가에서 남은 결함 정리 (툴 반복 KV 가드 · 임베딩 엔진 · 전경 진입 · 벡터 읽기 · 실험실 미러 · 문서)

## Context
0.41.5 마무리 뒤 받은 외부 평가 8항목을 코드와 대조했다(AGENTS §2-① — 외부 분석은 먼저 대조).
같은 보고서를 다른 세션에 재전달한 두 번째 의견(②·③-2·⑥)과 일치하고, 이 세션이 코드로 다시 확인한 ①·⑤ 와 문서 정리를 더한다.

### 대조 결과
- **유효 — 이 회차에서 고친다**
  - ⑤ **툴 반복 예산** — 예산 불변식(`TokenBudgetInvariantTest`)은 "대화 상한 2,800 + 툴 결과 **1개** 500 ≤ 천장 3,328(= KV 4,096 − 답 여유 768)" 만 보장한다.
    한 턴에 실행되는 툴은 **최대 2개**다(평가의 "3회"는 부정확 — `loopCount` 는 생성 횟수이고 3번째 생성의 툴은 0.40.2 부터 실행 전에 막힌다, `BaseAgent.kt:160`).
    2개째는 설계상 열린 길이다(기억 재검색·형식 오류 자가 수정, `BaseAgent.MAX_TOOL_LOOP_COUNT` [WHY]) — 첫 결과가 짧아 기본 예산 2,500 에서는 약 3,100 으로 천장 안,
    슬라이더 최대 2,800 + 재검색이면 약 3,400 으로 천장을 조금 넘는다(엔진 4,096 미만이나 답 여유가 준다). 턴 중간 KV 를 막는 장치는 없다(디버그 로그만 — `RuntimeDiagnostics`).
  - ① **임베딩 엔진** — `EmbeddingGemmaRunner.load()` 는 GPU 초기화가 실패하면 `null` 로 끝난다(채팅 엔진의 CPU 폴백 없음 — 에뮬레이터·GPU 메모리 부족이면 뜻 검색이 조용히 꺼짐).
    `LibraryEmbedder`·`MemoryEmbedder` 는 발열 판정(`shouldDeferBackgroundInference`)을 보지 않는다(요약·추출·브리핑·정리는 본다 — 민법 한 권이면 GPU 약 49초 연속).
    엔진은 앱이 백그라운드로 갈 때만 내린다. 채팅과 함께 떠 있으면 PSS 약 7.2GB(0.41.2) — 채팅만 약 4.9~5.0GB(0.37 FP32)와 **다른 날 잰 값**이라 임베딩 몫(약 2GB 추정)은 정확하지 않다.
  - ② `KosmosApp` 의 `ProcessLifecycleOwner.onStart` 가 `memoryEmbedder.onForeground()` 를 부른다 — 문서 뷰어(별도 Activity)만 열어도 15초 뒤 모자란 기억 벡터를 만들며 임베딩 엔진을 올릴 수 있다(ADR-027).
  - ③-2 `MemorySemanticRanker` 는 후보가 최근 메모·대화 500건씩인데 `vectors(modelId)` 로 **그 모델의 벡터 전부**를 읽는다 — 500건을 넘으면 읽고 버린다.
  - ⑥ 실험실 미러: `run.py` 의 반복 질문 판정에 앱(`RepeatedQuestions`)의 영어 의문사가 없다. `kosmos_lab.py` 는 "MTP 를 비우면 앱 현행과 같다"고 적혀 있으나 앱은 0.41.1 부터 ADAPTIVE(§2-⑤ 위반 둘).
  - ⑧ `docs/architecture.md` 1~14절(2026-07-31 판)의 기술 표 버전이 낡았고(Kotlin 2.3.21·AGP 9.2 …), 옛 평가 문서 `ENGINEERING_EVALUATION.md`·`INVESTOR_EVALUATION.md`(0.26 기준)가 `docs/` 에 남아 있다.
- **알고 정한 결정 — 손대지 않는다**: ③-1 일부만 준비되면 뜻 검색 끔(ADR-038 결정 3, 순위 왜곡), ④ 문서 턴 질문 중복(0.40.8 — exp46b 가 그 배치로 잼), ⑦-1 RESET 이 트랜잭션 밖(0.41.4 CHANGELOG), ⑦-3 백업 평문(ADR-032 사용자 결정).
- **사실과 다름**: ⑦-2 감사 체인 전수 로드(실제는 500행씩), RRF·코사인 하한 0.30(exp76b·78 에서 기각), 어간 추출·동의어 사전 31묶음(코드에 없음 — 쓰기 시점 태그 ADR-032), "TFLite 는 죽은 의존성"(OpenCL 선언을 넣고 있었다 — 0.41.5), "툴 최대 3회"(실행은 최대 2개).

## 결정 (사용자, 2026-11-06)
- **⑤ = 런타임 KV 가드** — 미리 계산한 예산(최악 가정)이 아니라 실제로 찬 양을 재고 판단한다. 한 턴 2번째 툴부터, 실행 **전에** `지금 KV + 툴 결과 상한 > 천장` 이면 실행하지 않고 앱 고정 문장으로 턴을 끝낸다
  (일정 추가 같은 부수효과가 일어나기 전에 멈춤 — "실행은 됐는데 답이 깨짐"이 없다). 앱 문장이라 모델 입력 불변. 0.42.x 여러 단계 계획에서 툴 횟수가 늘 때의 토대 — 이후 "멈춤" 대신 "앞 대화를 줄이고 이어 가기"로 넓힐 수 있다.
  (기각: 불변식을 결과 2개로 넓혀 테스트로만 고정 — 툴 횟수가 늘면 최악 가정이 예산을 바로 소진한다. 2·3번째 결과 상한 축소·반복 상한 축소 — 계산상 천장을 막지 못한다.)
- **① 임베딩 엔진 해제 = 실측 뒤 결정** — KV 캐시는 엔진을 올릴 때 4,096칸 분량을 **한꺼번에 잡는다**(0.15.x PC 실측: 칸 4,096 → 8,192 에 메모리 5.0 → 9.2GB, 토큰당 약 1MB).
  그래서 대화가 길어져도 메모리는 늘지 않고, 임베딩 엔진을 내렸다가 다시 깨워도 최고점은 지금(약 7.2GB)과 같다 — 내리기의 이득은 최고점이 아니라 **최고점에 머무는 시간**이다.
  대가는 1분 넘게 쉰 뒤 첫 검색에 엔진 올리는 0.9~2.5초. M1 첫 단계의 휴대폰 실측(아래)으로 "1분 안 쓰면 내리기" 를 넣을지 정한다.
- CPU 폴백(GPU 실패 시 CPU 로 한 번 더)과 발열 멈춤(묶음 사이에서 판정)은 그대로 넣는다(되돌릴 이유가 없는 보강).

## 고정 제약
- 기존 테스트 단언 불변(바꿔야 하면 먼저 보이고 확인). 모델 입력(지시·선언·리마인더·툴 결과 문구) 불변 — ⑤ 의 안내는 앱 말풍선이라 모델 입력이 아니다.
- 실험실 미러를 고치므로(⑥) 모델 회귀 세트를 다시 돌리고 기준값과의 차이를 CHANGELOG 에(§2-⑤ 예외 규칙). 기준값 갱신은 결과 확인 뒤에만.
- 백그라운드에서 모델(임베딩 포함)을 올리지 않는다(§2-⑥). 시각 판정은 `now` 주입(§2-④).

## 마일스톤

### M1 — 실측: 메모리 (휴대폰, 디버그 빌드)
같은 앱 실행 안에서 `dumpsys meminfo` PSS(+ GPU 메모리가 보이면 함께):
1. 채팅 엔진만 — 첫 짧은 대화 직후 / 긴 대화(KV 약 3,000) 뒤 → **KV 가 처음에 잡히는지** 휴대폰에서 확인.
2. 임베딩 엔진을 올린 뒤(서랍 검색 한 번) → 임베딩 몫이 정확히 몇 GB 인지.
3. 임베딩 엔진을 내린 뒤(디버그 손잡이로 `release`) → 메모리가 실제로 돌아오는지(네이티브 메모리는 닫아도 바로 안 돌아오는 경우가 있다).
결과로 "1분 안 쓰면 내리기"의 채택을 정한다(사용자에게 수치 보고 후). 수치는 CHANGELOG 에.
**결과 (2026-11-06, SM-S938N)**: 채팅 엔진만 PSS 6.46~6.97GB(GPU 5.59~5.81GB) — KV 1,228 → 2,607 에도 GPU 그대로(**KV 는 처음에 잡힌다**). 채팅 + 임베딩 6.99GB(GPU 5.98GB) → **임베딩 몫 GPU 약 0.2~0.4GB**(2GB 추정은 다른 날 값의 뺄셈 착시). 홈으로 나가 두 엔진을 내리면 0.35GB(**닫으면 돌아온다**). MTP 를 꺼도 GPU 5.73GB(MTP 몫 아님). → **1분 해제는 넣지 않는다**(사용자 결정 — 이득 약 0.3GB 대 검색마다 0.9~2.5초). 채팅 엔진이 0.37 기록(약 4.9GB)보다 1.5~2GB 큰 원인은 범위 밖(옛 빌드 비교가 필요, 사용자 결정으로 생략) — README·사용 안내의 "약 5GB" 는 M6 에서 고친다.

### M2 — 툴 반복 KV 가드 (⑤)
`ModelRunner` 에 지금 대화의 KV 토큰 수 조회(`currentKvTokens(): Int?` — 엔진·대화가 없으면 null, 판정 생략). `BaseAgent` 가 한 턴 2번째 툴부터 실행 전에 판정 —
넘으면 실행하지 않고 대화를 비운 뒤(`invalidateConversation` — 회신 없는 툴 호출을 KV 에 남기지 않는다, 0.40.2 상한 경로와 같은 처리) 고정 안내 말풍선(한·영) + 감사 기록 ERROR.
판정식은 순수 함수(`ToolBudget.fits(currentKv, resultCap, ceiling)`)로 분리해 경계값 테스트. `TokenBudgetInvariantTest` 에 "첫 툴 결과는 불변식, 2번째부터는 런타임 가드" 를 고정하는 테스트(기존 단언 불변).
테스트: 여유 있음 → 실행, 넘음 → 미실행·안내·감사, 조회 불가(null) → 실행(지금 동작).

### M3 — 임베딩 엔진 (①)
`EmbeddingGemmaRunner`: GPU 실패 시 CPU 로 한 번 더(백엔드 로그). 유휴 해제는 넣지 않는다(M1).
`LibraryEmbedder`·`MemoryEmbedder`: 묶음마다 발열 판정 → 넘으면 멈춤(문서는 기존 `Paused` — 답 끝·전경·버튼에서 이어 감, 기억은 남은 것이 다음 계기에). 새 문자열이 필요하면 한·영 함께.
테스트: 폴백(GPU 실패 → CPU), 발열 멈춤.

### M4 — 전경 진입·벡터 읽기 (②·③-2)
`memoryEmbedder.onForeground()` 를 `MainActivity` 쪽(ModelWarmUpObserver 와 같은 자리)으로 — 뷰어만 열면 부르지 않는다. 백그라운드 멈춤(`onBackground`)은 프로세스 단위에 그대로.
`MemoryVectorRepository` 에 키 목록으로 읽는 조회를 더해 랭커가 후보 벡터만 읽는다(SQLite 변수 상한 999 → 묶어서 읽기).
테스트: 후보만 읽기(500 초과 데이터), 뷰어 경로에서 onForeground 미호출.

### M5 — 실험실 미러 (⑥)
`run.py` 반복 질문 판정에 영어 의문사(앱 정규식 그대로), `kosmos_lab.py` MTP 기본을 앱과 같은 ADAPTIVE 로(끄려면 `off` — 문서 문구 정정).
모델 회귀 세트 다시 실행 → `baseline.json` 과의 차이를 CHANGELOG 에(기준값 갱신은 확인 뒤).

### M6 — 문서·실기기
README·사용 안내 한·영의 "실행 중 약 5GB" 를 M1 실측(약 6.5~7GB)으로. `architecture.md` 1~14절 머리에 "v0 설계 당시 기록 — 정본은 15절 ADR·`libs.versions.toml`" 표지, 기술 표의 버전 열은 숫자 대신 카탈로그 링크(§3-② 베낀 숫자 금지). 옛 평가 문서 2개를 `docs/archive/` 로(링크 `docs/README.md`·CHANGELOG 확인).
실기기: 채팅 중 문서 색인 → 발열 판정 로그, 뷰어만 열기 → 임베딩 엔진 안 뜸, 기억 재검색 턴 한 번(가드 로그).
CHANGELOG 0.41.6, ADR-020 보충(턴 중간 KV — 런타임 가드), ADR-037·038 보충(엔진 수명), ADR-027 보충(기억 준비도 화면 단위), 계획서 완료 표시.
