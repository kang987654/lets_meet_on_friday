# LiteRT-LM 0.16.0 → 0.18.0 · GPU 활성화 정밀도 재검토 (0.37.0)

## Context

- **런타임**: 앱은 `litertlm-android` 0.16.0(`gradle/libs.versions.toml`). 0.18.0(2026-10-06)이 나왔고 gallery 도 0.18.0 이다.
  릴리스 노트(0.16.1·0.17.0·0.17.1·0.18.0) 중 우리 관련: 0.17.0 로컬 어텐션 최적화(메모리·긴 문맥), 0.17.1 툴 호출 정수 인자 수정
  (우리 선언엔 정수 파라미터 없음), 0.18.0 `ModelInfo` API·GPU 어텐션 마스크 최적화. EmbeddingGemma 2·Metal·12B 는 무관.
- **릴리스 노트에 없는 큰 변화 (AAR classes.jar 비교, 2026-10-14)**: 0.18.0 `EngineConfig` 생성자 끝에 **`activationDataType: ActivationDataType?`**
  (`FLOAT32`·`FLOAT16`·`INT16`·`INT8`)가 생겼다. ADR-021 은 GPU 숫자 깨짐의 원인을 **텍스트 디코더 FP16 활성화 × 문맥 깊이**로 확정했고
  (PC GPU exp29-E: FLOAT32 면 온전), 처방 후보 `activationDataType = FLOAT32` 를 **"AAR 0.16.0 이 노출하지 않아 불가"** 로 기각한 뒤
  예산을 발병점 아래(1,700)로 낮췄다. 그 기각 사유가 사라졌다.
  - 그 외 클래스 변화: 추가 — `ModelInfo`(`Llm`·`Embedding`·`Unknown`)·`LlmCapability`·`Modality`·`BackendType`·`NpuBrand`·`SamplerParameters`·
    `Embedding*`. **제거 — `Capabilities`**(앱은 쓰지 않음, grep 0건).
- **PC 재현 가능성**: ADR-021 의 판정(exp27~30)은 이 PC(RTX 4070 Laptop, 같은 모델 파일 3,659,530,240 바이트) 실험실에서 했고 스크립트가
  추적돼 있다. 파이썬 `litert-lm` 도 **0.18.0 이 있어 앱과 같은 버전으로 맞출 수 있다**(0.16 당시엔 파이썬이 앞서 있었다). 다만 그때의
  프롬프트(시스템 지시·오버헤드 ~1,400)와 지금(`MEASURED_OVERHEAD` 1,250)이 달라 **발병점은 현 픽스처로 다시 잰다** — 같은 하네스에서
  0.16.0 과 0.18.0 을 나란히 돌려야 버전 효과를 가를 수 있다(§2-⑤ "실험은 새로 짠다", exp27 의 깊은 문맥 재료는 재사용).
- **PC↔기기 한계(ADR-021)**: PC GPU(WebGPU/NVIDIA)의 발병점이 Adreno 와 같다는 보장은 없다 — 0.13 회차에서는 PC 발병점이 기기에도 유효했지만,
  **최종 판정은 실기기**다.

## 고정 제약
- **단독 변경**: M1 은 카탈로그 한 줄만 바꾼다(다른 의존성·코드 무변경) — 기기에서 달라진 것을 런타임에 귀속하려면(0.16.0 상향 전례, ADR-019).
- 활성화 정밀도·예산 변경(M3)은 M2 실기기 결과로 **사용자가 결정**한다 — 실측 없이 예산을 올리지 않는다.
- 예산을 올리면 `TokenBudgetInvariantTest` 의 발병점·루프 방지 단언이 바뀐다 → **대상 단언을 먼저 보여 주고 확인 후**(§2-②).
- 실기기 확인은 이전 회차 규칙 그대로: 앱 밖 흔적·기존 데이터 변경 없음, 다른 앱·알림 읽지 않음, 설정·권한은 사용자가 탭, PC 사본은 분석 후 삭제.
- 실험실은 conda `friday` 를 0.16.0 기준선으로 두고, 0.18.0 은 **복제 환경**(`friday18`)에 설치해 A/B 한다.

## 결정할 것 (승인 시)
- **D1 M3 범위**: M2 결과를 보고 정한다 — (a) 0.18.0 상향만, (b) + FLOAT32 활성화(예산 유지, 툴 회신 턴 ~2,350 노출 해소),
  (c) + FLOAT32 + 예산 상향(히스토리 늘림).

## 마일스톤

### M0 실험실 실측 (PC, 코드 무변경) — `scratch/lab/exp51_runtime_018.py`
현 픽스처(`PromptFixtureExportTest` 내보내기)와 exp27 의 깊은 문맥으로, 같은 스크립트를 `friday`(0.16.0)·`friday18`(0.18.0)에서 돌린다. greedy 라 지점당 1회, 경계 2회.
1. **발병점 재측정**: GPU·FP16(기본) 깊이 스윕(토큰 1,600~3,000, 판정 = exp27 판정 발화의 `start_time` 온전 여부 + 비밀번호 회수 숫자) — 0.16.0 vs 0.18.0.
   0.18.0 의 GPU 어텐션 변경으로 발병점이 움직이는지.
2. **FLOAT32 활성화**: 0.18.0 GPU·FP32 로 같은 스윕을 4,096 근처까지 — 깊은 문맥에서도 온전한지.
3. **비용**: FP16 vs FP32 의 prefill·decode 토큰/초, 첫 토큰 시간, 프로세스 메모리(PC 기준 — 기기 수치는 M2).
4. **툴 호출 스모크**: exp41 계열(23건) 0.18.0 FP16·FP32 — 툴 선택·인자 회귀 없음. 0.17.1 정수 인자 수정이 우리 인자(문자열)에 영향 없는지.
5. **멀티모달 대조**: 이미지 1건·오디오 1건(exp32b 계열) — 백엔드 구성 그대로 동작.
- **판정**: 0.18.0 FP16 이 0.16.0 과 같거나 낫고 툴 스모크 무회귀면 M1 진행. FP32 결과는 M3 판단 재료로 CHANGELOG 에 남긴다.
