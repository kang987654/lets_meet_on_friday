# 0.42.4 채팅 밖 추론 폭주 · 긴 메모 임베딩

> **상태**: 승인 (2026-11-17, 계획대로 — 사용자 "가능한 빠르게"). 계획·구현·검증 Claude 한 세션.
> 정본 순서: **AGENTS.md > 이 계획서**.
> 근거: 2026-11-17 휴대폰 확인(0.42.3 설치 뒤, SM-S938N). 회차 성격: 휴대폰에서 찾은 것(버전 규칙 끝 숫자).

## 휴대폰에서 본 것 (로그, `adb logcat` PC 로만)
| 프로세스 | MTP | 회고 oneShot | 대화 합치기 판정 | 그 전에 뜻 검색 임베딩 엔진 |
|---|---|---|---|---|
| 17:18 시작 | ADAPTIVE(실제 꺼짐, 17토큰/초) | 99토큰, 정상 | 3토큰, 정상 | 올라온 흔적 없음 |
| 17:23 다시 뜸(사용자가 최근 앱에서 밂) | ADAPTIVE(실제 켜짐, 33토큰/초) | **3,759토큰 깨진 글자**(약 2분) | 3,807토큰 깨짐 | 17:24:10 GPU 로 올라와 1건 임베딩 |
| 17:32 다시 뜸(`debug_mtp.txt` = OFF) | OFF | 120초 감시 초과로 중단 | 120초 초과 | 17:32:38 GPU 로 올라와 실패 |

- oneShot 은 스트리밍이 아니라 감시가 **총시간**을 잰다 — OFF(17토큰/초)에서 같은 길이를 내면 120초를 넘는다. 즉 세 번째도 "멈춤"이 아니라 같은 **폭주(끝없는 깨진 출력)**로 보인다 → MTP 는 원인이 아니다.
- 이상했던 두 번 모두 앱을 막 켠 뒤 **임베딩 엔진이 GPU 에 같이 올라온 상태**에서 정리가 돌았다(정상이던 첫 번째는 흔적 없음). 가설 H1: 채팅 엔진과 임베딩 엔진이 GPU 에 함께 있으면 oneShot 출력이 깨진다. 확정 아님.
- 함께 찾은 결함: ① oneShot 에 출력 상한이 없어 깨진 출력이 엔진 한도(4,096)까지 간다. ② 깨진 회고가 그대로 기억(메모)으로 저장됐다(3,831자).
  ③ 그 메모가 512토큰을 넘어 뜻 검색 벡터 만들기가 **묶음째** 실패한다("Input sequence length (618) exceeds maximum supported signature length (512)") — 긴 메모 하나가 뜻 검색 준비 전체를 막는다(원래 있던 결함).
  ④ 회고가 실패해도 정리 화면은 "지난 7일 동안 정리된 대화가 없어 회고를 만들지 않았어요"(실패를 없음으로 보임).
- 4번(정리 중단 안내)은 최근 앱에서 밀어 프로세스가 죽어 판단 불가 — 다음 휴대폰 확인 때 **홈 버튼**으로 다시.

## 결정 (승인 때 정할 것)
- **D1 원인 확인 순서** — 먼저 휴대폰에서 H1 을 가른다(M1). 결과에 따라 근본 처방을 고른다:
  H1 이 맞으면 (가) 채팅 밖 추론 전에 임베딩 엔진을 내린다 / (나) 임베딩을 CPU 로(속도 43 → 83ms/개, 0.41.2 실측) 중 실측으로. 틀리면 원인을 더 좁히고 이 회차는 안전장치(D2)만.
- **D2 원인과 상관없는 안전장치(바로)** — ① oneShot 출력 상한(용도별 — 회고·요약은 넉넉히, 판정은 짧게; 실측한 정상 길이의 몇 배) ② 회고·요약·추출 결과 검사: 상한에 닿았거나 글자가 깨졌으면(한글·영문 비율 등 간단한 규칙) **저장하지 않고 실패로** ③ 임베딩 입력을 토큰 상한에서 자르기(`InputOverflowStrategy.TRUNCATE` — 실험실 exp94 와 같은 옵션) ④ 회고 실패 문구를 "회고를 만들지 못했어요"로.
- **D3 이미 저장된 깨진 회고** — 고친 뒤 정리를 다시 돌리면 같은 주 회고로 덮어써진다(주차 키 id). 따로 지우는 마이그레이션은 하지 않는다(시험 데이터, 사용자 확인).

## 고정 제약
- 백그라운드 모델 로드 금지·`oneShot = true`(§2-⑥) 불변. 채팅 모델 입력 불변 → 회귀 세트 대상 아님(출력 상한은 채팅에 걸지 않는다).
- 휴대폰: 진단은 GPU 문제라 휴대폰에서만 — 미리 무엇·왜·몇 분을 말하고, 디버그 파일(`debug_embed.txt`·`debug_mtp.txt`)은 끝나면 지운다. 사용자는 그동안 휴대폰을 만지지 않는다(최근 앱 밀기 금지).
- 기존 테스트 단언 불변. 새 테스트: 상한·검사·자르기·실패 문구.

## 마일스톤

- 0.42.4 · 42004, 이 계획서.

### M1 — 원인 확인 (휴대폰 약 10분)
- 같은 순서로 두 번: 앱 강제 종료 → 켜기 → 엔진 준비 → 기억 정리 → 회고 길이·깨짐·속도(`bench`) 기록.
  A = `debug_embed.txt` 에 CPU(임베딩이 GPU 에 없음), B = 파일 없음(GPU 기본). 가능하면 각 두 번. 그 전에 깨진 메모 때문에 임베딩이 실패하는 상태가 결과를 흐리지 않게 순서를 적어 둔다(실패해도 엔진은 올라온다).
- 결과를 CHANGELOG 에 표로. 계획과 갈리면 [WHY]·CHANGELOG.

### M2 — 안전장치 (D2)
- `ChatPrompt` 에 출력 상한(기본 null = 채팅 무제한) → `GemmaModelRunner` oneShot 경로에서 `maxOutputToken`. 용도별 값은 실험실 정상 출력 길이(exp96·97 의 요약·회고·판정)로 정한다.
- 결과 검사: 상한에 닿으면 실패. 깨진 글자 규칙은 간단히(허용 문자 비율) — 회고·요약·추출 저장 앞에서.
- 임베딩 `EmbeddingOptions(normalize = true, inputOverflowStrategy = TRUNCATE)` — 테스트로 옵션 고정(기기 없이 확인 가능한 범위).
- 회고 실패 문구 한/영.
