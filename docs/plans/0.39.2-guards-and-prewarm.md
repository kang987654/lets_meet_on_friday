# 0.39.2 — 보정 장치 정리 + 재생성은 답 직후 미리

## 목표
1. 0.13~0.38.9 에 쌓인 모델 행동 보정 장치를 **한 목록(ADR)** 으로 만들고, `BaseAgent.executeToolLoop` 에 섞여 있는 장치를
   "툴 실행 전 가드 / 답 후처리" 단계로 나눈다. 장치끼리 겹쳐 잘못 걸리는 경우를 회귀 세트로 잡고, 실측된 것만 고친다.
2. 대화 재생성 비용(0.39.0 M1: 재생성 턴 +6~7초)을 **다음 질문에서 답 직후로** 옮긴다.

## 정한 것 (2026-10-29 사용자)
1. **답이 끝나자마자(화면·저장 뒤) 뒤에서 대화를 미리 다시 만든다** — 거절 답 · 앱이 고친 답 · 앱이 연 저장 · 거절 되묻기 뒤.
   그 사이에 보낸 질문은 남은 시간만 기다린다. 미리 만든 대화를 다음 질문이 다시 버리는 경우(거절 되묻기 등)만 지금보다 한 번 더 만든다.
2. **예산이 찬 경우도 답 직후 정리하고 미리 만든다** — 대화 정리(리셋 이벤트·에피소드 닫기)가 "다음 질문 시작"에서 "직전 답 끝"으로 당겨진다. 요약은 그대로 60초 조용해진 뒤.
3. **컨텍스트 막대(얼마나 찼는지 · 항목별 몫)와 "지금 정리" 버튼은 0.39.3** — 토큰 예산 실측과 함께. "지금 정리"는 이 회차의 미리 만들기를 쓴다.

## 지금 알고 있는 것
- 재생성 표식: `ModelRunner.invalidateConversation()` → `GemmaModelRunner.conversationStale`. 다음 **사용자 턴**의 `getOrCreateConversation` 이
  DB 히스토리로 대화를 새로 만든다(툴 회신 턴은 그대로). 호출처: `BaseAgent` 4곳(거절 되묻기 시작·승인 거절·고친 답·거절 답/되묻기 끝), `ReminderEditor`(화면에서 고친 알림).
- 예산 정리: `decideConversation` 이 캐시 대화의 `getTokenCount()` 가 `conversationResetThreshold` 를 넘으면 `Recreate(TOKEN_BUDGET)` — 리셋 이벤트 → `EpisodeBoundaryManager`.
- 시스템 지시는 **하루 동안 고정**(PromptAssembler — 분 단위 시각은 턴 리마인더), 캐시 키는 세션·시스템 지시·툴 목록 → 답 직후 만든 대화를 다음 턴이 재사용할 수 있다(날짜가 바뀌거나 설정을 바꾸면 다시 만든다 — 지금과 같음).
- 0.39.1 M0(exp65): 대화 상태 복원 비용은 **첫 호출에 붙는다** — 새로 만든 대화의 히스토리 프리필이 생성 시점인지 첫 `getTokenCount`/`send` 시점인지는 모른다(M0 c 에서 잰다).
- 엔진은 한 번에 하나만 추론(`llmDispatcher` 단일 스레드 + 뮤텍스). 네이티브 추론 중 취소는 0.38.6 결함 경로 — 미리 만들기는 취소하지 않는다.

## 마일스톤 (각각: 게이트 → 커밋)
- **M0 실측 (코드 수정 0)**
  - a. **장치 목록** — 위치 · 원인 실험 · 판정이 틀릴 때 어느 쪽으로 깨지는가 · 비용(토큰 · 재생성 · 추가 DB 읽기). ADR 초안이 된다.
  - b. **겹침 케이스를 회귀 세트에** (`scratch/lab/regression/run.py` 새 세트) — 예: 실제로 답한 턴의 "직접 해 드릴 수는 없지만 …"이 거절로 빠지는가,
    되묻기와 저장 낱말이 함께 있는 말, 저장이 아닌 물음 뒤의 "응", 거절 되묻기 판정이 일상 말("왜 안 와?")에 걸리는가. 실기기 대화 모양으로. 결과를 보고 기준값에 넣는다.
  - c. **미리 만들기가 비용을 다 치르는가 (PC 실험실, exp66)** — 히스토리를 실은 대화 생성 → (토큰 수 조회) → 다음 send 첫 글자. 생성만 / 조회까지 / 아무것도 안 함을 대조.
- **M1 단계 분리 (행동 불변)** — `BaseAgent` 의 실행 전 가드(allowlist · 되묻기 · 사실 저장)와 답 후처리(ISO 변환 · 약속 문장 · 앱이 연 저장 · 거절 재생성 표식)를
  각각의 클래스로. 막아 둔 메모(`blockedMemo`)를 에이전트 필드에서 세션 단위 보관으로. 기존 테스트 단언 그대로 + 단계별 단위 테스트 + 회귀 세트로 불변 확인.
- **M2 겹침 고치기 (M0 b 결과에 따라)** — 실측으로 잘못 걸린 것만. 판정식을 바꾸면 회귀 세트의 흉내도 같이(AGENTS §2-⑤), 차이를 CHANGELOG 에.
- **M3 답 직후 미리 만들기** — 모델 런너에 "필요하면 지금 다시 만들기"(재생성 표식이 있거나 예산을 넘었을 때만, 아니면 아무것도 안 함)를 두고,
  턴이 끝난 뒤 오케스트레이터가 다음 턴과 같은 프롬프트(기록·지시·툴)로 부른다. 실패는 무시(다음 턴이 지금처럼 만든다). M0 c 결과대로 프리필까지 치른다.
  테스트: 표식 없고 예산 안이면 안 만듦 · 표식이면 만들고 다음 턴 재사용 · 예산 초과면 리셋 이벤트가 답 직후 · oneShot·툴 회신 턴 무관.
- **M4 실기기 확인** — 4경로 + 예산 정리의 다음 질문 첫 글자(0.39.0 M1·0.39.1 M3 와 같은 디버그 빌드로 비교), 미리 만드는 중에 바로 보낸 질문의 대기. `scratch/lab/device/`.
- **M5 마무리** — 장치 목록 ADR(architecture.md ADR-030) · 설명 문서 `docs/decisions/06` 갱신 · CHANGELOG · 계획서 상태 · 로드맵.

## 예산·실측 수칙
- 미리 만들기는 모델 입력을 바꾸지 않는다(같은 프롬프트를 일찍 만들 뿐) — `MEASURED_OVERHEAD` 그대로.
- M1·M2 는 모델 행동 가드를 건드리므로 회귀 세트를 돌리고 `baseline.json` 과의 차이를 CHANGELOG 에 적는다. 기준값 갱신은 결과 확인 뒤.
