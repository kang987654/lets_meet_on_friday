## 원칙 (AGENTS·04_MODEL_EVIDENCE 그대로)
- **실측 선행**: 회차는 M0 실측(코드 수정 0, 측정용 임시 로그는 커밋 안 함)으로 시작하고 결과로 "진행 / 닫기"를 정한다. 수치에는 근거 등급, 없으면 "모른다".
- 계획서는 구현 전에 커밋, 마일스톤마다 `./gradlew test lintDebug assembleDebug`, 기존 단언 수정은 사용자 확인 후.
- 모델 입력이 바뀌면 실험실 실측 → `MEASURED_OVERHEAD` 갱신(지금 여유 35) → 부족하면 대화 기록 몫이 줄어드는 대가를 적고 승인 후 예약 증액.
- 성능 수치는 디버그 빌드로 판단하지 않는다 — 최적화 빌드로 잠깐 재고 되돌린다(0.38.9 M5).
- **새 기능보다 핵심 신뢰도 먼저** — "말하면 맞게 하고, 못 하면 정직하게 말한다"의 잔여 실패가 있는 동안 새 화면·새 툴은 바닥 다지기 뒤로.
- **회차 끝 독립 리뷰** — 작업한 세션과 별개로(새 세션·`/code-review`) 변경분만 주고 짧게(`docs/agent_workflow_guide.md` v3.0).

  지금 "첨부해서 묻기"로는 왜 안 되는가.
- **M0**: 실제 대상 문서(예: 50쪽+ 규정집)로 첨부 방식이 어디서 실패하는지. **M1**: 구조 인지 청킹 + 표 선형화(exp46c) + 바이그램을 청크 단위로 넓혀
  회수율(exp33 방식). 부족할 때만 Kiwi·FTS5·임베딩 비교. 기억 검색과 엔진·저장소 분리를 ADR 로. 새 툴은 0.39.3 의 여유 안에서.

### 기기 범위 (공개 레포)
- README 에 요구 사양·에뮬레이터 실행법(위 "지금 바로"). 8GB 기기는 메모리(GPU FP32 PSS 약 5GB — ADR-029)가 핵심 — 작은 모델은 "확인 필요"가 풀린 뒤
  툴 호출 정확도를 다시 재는 큰 회차로.

### 후보 (근거가 생기면)
- 실기기에서 실행 중 GPU 실패 시 CPU 로 바꾸는 폴백(외부 검토의 권고) — 지금 CPU 폴백은 초기화 실패에만 걸린다. 실기기에서 실행 중 실패가 관측될 때 회차로.

### 보류 (제품 방향)
- B2B(의료·법률·금융 폐쇄망) 전환 — 외부 검토 비판 6 의 제언. 엔지니어링이 아니라 제품 방향 결정이라 지금은 개인 비서의 장점(오프라인·개인 기억·감사 기록) 극대화로 둔다.

### 나중 (개발이 굳은 뒤)
- 개인용 최적화 빌드(R8) + 주요 흐름 확인 회차(0.38.9 M5 사용자 결정).

## 사용자가 정할 것 (회차를 열 때)
1. 문서 검색의 제품 정의(0.4x).
2. 음성에서 실제로 불편했던 점 — 0.39.0 M1 의 합격 기준.
3. 기기 범위(에뮬레이터 검증까지 / 8GB 기기까지).
4. 저장 데이터 보호의 위협 모델.
