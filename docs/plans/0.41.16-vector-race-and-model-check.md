## 목표
1. **R1 기억 벡터 경합** — `MemoryEmbedder.drain` 이 대상(메모·요약된 대화)의 글을 읽어 임베딩하는 몇 초 사이에 사용자가 그 메모를 고치거나 지우면:
   - 고침: 저장소가 벡터를 지운 뒤(`KnowledgeRepositoryImpl.save`) 끝난 묶음이 **옛 글의 벡터**를 다시 넣는다 → "벡터 있음"으로 보여 다시 만들지 않아 뜻 검색이 옛 내용으로 굳는다.
   - 지움: 지운 메모의 벡터가 남는다(검색은 메모 목록에서 걸러져 안 보이지만 행이 쌓인다).
   - 0.41.9 판단: 드물다, 버전 열 추가(마이그레이션) 설계가 필요해 미룸.
2. **L5 모델 파일 검사** — 라이브러리의 `ModelInfo.from`(LiteRT-LM)으로 3.6GB 모델을 올리기 **전에** 파일이 맞는지 본다. 0.41.9 판단: API 는 있으나 앱이 직접 받은 파일이라 이득이 작음.
   지금은 사용자 URL 다운로드·adb 로 넣은 파일도 있어, 깨진·다른 형식 파일일 때 어떤 안내가 나오는지가 관건.

## 결정 (사용자 승인 2026-11-16)
- **D1 R1 처방 — (가) 저장할 때 대조 (추천, 마이그레이션 없음)**: 벡터를 저장하는 트랜잭션 안에서 대상의 **지금 글**을 다시 만들어, 임베딩에 쓴 글과 다르거나 대상이 없으면 그 벡터는 넣지 않는다.
  안 넣은 것은 "벡터 없음"으로 남아 다음 준비 때 새 글로 다시 만들어진다. 비용은 저장 때 대상 몇 건 다시 읽기.
  (나) 벡터 행에 글의 해시 열을 더하고 "해시가 다르면 다시 만들기" — 마이그레이션(DB v14 → v15)과 기존 벡터 전부 재생성이 따른다.
- **D2 L5 — 확인 뒤 결정**: M2 첫 단계에서 ① `ModelInfo.from` 이 실제로 무엇을 검사하는지(라이브러리 jar 로) ② 지금 깨진 파일을 넣으면 어떤 안내가 나오는지(JVM·에뮬레이터)를 보고,
  지금 안내가 이미 쓸 만하면 **넣지 않고 기각으로 기록**한다. 넣을 가치가 있으면 그때 보여 드리고 진행.

## 고정 제약
- 기존 테스트 단언 불변. 저장소 인터페이스에 메서드를 더할 때는 기본 구현을 둬 테스트의 가짜 구현이 그대로 컴파일되게 한다.
- 보관함 뜻 벡터(`LibraryEmbedder`)도 같은 경합이 있는지 M1 에서 확인 — 조각은 다시 색인하면 새 행 id 라 옛 벡터가 고아로 남을 수 있다(0.41.14 에서 지운 문서는 막음). 있으면 같은 방식으로, 크면 멈추고 묻는다.
