# 0.39.3 — 고정 몫을 줄여 대화 기록 자리 늘리기 · 헤더 캡슐이 원인을 말하게

## 목표
1. 시스템 지시·툴 선언·턴 리마인더(고정 몫)를 실측으로 줄이고, 얻은 자리를 **대화 기록**에 준다 — 지금 기록 자리는 약 600~1,100토큰(2~4턴)이라 자동 정리가 잦다.
2. 헤더의 별이 노랑(발열)·빨강(엔진 오류)일 때 **원인이 화면에 보이게** — 캡슐 글자와 상태 시트.

## 정한 것 (2026-10-30 사용자)
1. 얻은 자리는 대화 기록에(새 툴을 넣을 때 다시 나눈다).
2. 컨텍스트 막대 · "지금 정리" 버튼은 **뺀다** — 0.39.2 부터 예산을 넘으면 답 직후 앱이 정리하므로 수동 버튼은 드물게만 쓸모 있다. 별 색은 엔진 상태 그대로(노랑·빨강을 대화 용량에 쓰면 발열·엔진 오류와 겹친다).
3. 화면: 캡슐 글자가 원인을 말한다 — 발열 경고면 "발열 주의 43°", 엔진 오류·모델 없음이면 "엔진 오류"/"모델 없음". 캡슐을 누르면 시트에 **원인 문장과 "다시 시도"**(설정의 다시 시도와 같은 경로).
   별을 누르는 설명은 두지 않는다(사용자: 불필요).

## 마일스톤 (각각: 게이트 → 커밋)
- **M0 실측 (코드 수정 0)** — ① 재사용 대화의 턴당 KV 증가 분해(리마인더가 쌓이는가) ② 줄일 후보별 토큰 절감(tokenize): 선언 설명·인자 설명 다듬기, 선언과 트리거 규칙의 중복,
  시스템 지시 문장 정리, 리마인더 축약, 툴 조건부 노출 ③ 지금 대표 대화 모양에서 몇 턴 만에 정리되는가(기본 예산·최소 예산) ④ 선택 인자 되묻기의 재현 빈도(기록이 있는 대화).
  결과로 후보 목록과 예상 절감을 사용자에게 보이고 실험할 후보를 정한다.
  - **M0 결과 (exp67, PC GPU)** — ① 짧은 대화 한 턴의 KV 증가 약 +100 중 **리마인더 61**(사용자 7~11 · 답 16~19 · 형식 10) — 재사용 대화에서는 지난 턴의 리마인더가 KV 에 남는다(재생성한 대화는 DB 기록이라 없다).
    ② add_schedule 191 = 형식 구조 96 + 설명 95(예시 둘 28, 선택 인자 end_time·memo 둘 66). ③ 일상 대화(답 길이 자유)에서 첫 KV 1,357, 턴마다 +200~400 —
    정리 기준 2,000 은 4턴째, 2,500 은 5턴째, 2,800 은 6턴째에 넘는다. ④ 선택 인자 되묻기: 기록 4종 × 문장 4 = 16건 중 0 — 드문 일로 보고 회귀 `optional` 로 지켜보기만.
    후보별 절감(tokenize): 리마인더 축약 61→40(**턴마다 −21**) · get_schedule date 설명 53→15(−38) · 상대 날짜 문단 78→39(−39) · add_schedule 예시 제거(−28) ·
    search_memory 설명 30→10(−20) · add_schedule memo 인자 제거(약 −33). 고정 몫 합계 최대 약 −158(1,384 → 약 1,226).
    참고: M4(0.39.2) 실기기에서 정리가 KV 2,030 에서 일어났다 — 휴대폰의 대화 예산이 최소값 2,000 근처로 보인다(추정, 설정 화면 미확인). 기본 2,500 이면 그것만으로 자리 +500.
- **M1 후보 실험실 A/B** — 후보마다 회귀 세트 전체(`scratch/lab/regression/run.py` — 모델 입력을 바꾸므로 AGENTS §2-⑤). **기준에서 새로 깨진 행동이 없는 후보만 채택**.
  흉내(`kosmos_lab.py` 툴 미러·픽스처)를 앱 문구와 함께 바꾼다.
- **M2 앱 반영** — 채택한 문구를 `PromptAssembler`·`KosmosToolDeclarations` 에. `MEASURED_OVERHEAD` 재측정, 예약(`PREFILL_OVERHEAD_TOKENS`)을 낮춰 기록 몫을 늘림 — `TokenBudgetInvariantTest` 불변식 유지.
  회귀 세트 전체(+ `--prewarm`) 차이를 CHANGELOG 에, 기준 갱신은 결과 확인 뒤.
- **M3 헤더 캡슐·상태 시트** — 캡슐: 발열 경고면 "발열 주의 n°"(warning), 엔진 오류·모델 없음이면 "엔진 오류"/"모델 없음"(danger, 아이콘 포함 — 색만으로 전하지 않음).
  시트: 원인 문장(`ErrorMessages.userMessage` — 시작 화면과 같은 문구) + "다시 시도". `docs/DESIGN.md`(토큰·Phosphor·AppTypography) 준수, impeccable 점검, 라이트·다크.
  E2E 계약 문자열·`ChatScreen` 기본 인자 그대로(AGENTS §2-②).
- **M4 실기기 확인** — 같은 대화 모양에서 정리까지 턴 수(전·후), 툴 스모크 몇 개, 캡슐·시트 육안(라이트·다크). 발열·엔진 오류는 실기기에서 일부러 만들기 어려워 화면 테스트로만 본다 — 실기기 확인 목록에도 남기지 않는다(사용자: 문제가 생기면 그때 확인).
- **M5 마무리** — CHANGELOG · ADR(예산 몫 조정) · 사용 안내(한·영, 캡슐 글자) · README 한계 표 · 계획서 상태 · 로드맵.

## 예산·실측 수칙
- 문구 하나의 비용은 `engine.tokenize` 차이로(대화 `token_count` 에는 응답 길이가 섞인다 — exp41). 오버헤드 실측 → `MEASURED_OVERHEAD` → 예약 조정 순서.
- 회귀 세트는 흔들림(실행 간 ±1)이 있다 — 새로 깨진 항목은 답을 읽고, 판정식·입력이 닿지 않는 것은 흔들림으로 기록한다(0.39.2 교훈: 확인 실험에서 모델이 실제로 그 경로를 탔는지부터).
