## 1. 일하는 방식 (회차마다 반복)
1. **계획서**: 회차를 열면 `docs/plans/<버전>-<회차명>.md` 를 이 런북의 해당 절로 만든다(상태: 승인 — 이 런북으로 사전 승인됨). 커밋: `docs(plan): <버전> … 계획`.
2. **M0 실측 먼저**(코드 수정 0, 측정용 임시 로그는 커밋 안 함) → 결과로 "진행 / 닫기"를 정하고 계획서에 `- **M0 결과**: …` 줄로 적는다.
3. **마일스톤마다**: 구현 → `./gradlew test lintDebug assembleDebug` 녹색 → staged 목록 확인 → 커밋(한 줄 제목). 계획서에 `- **Mx 결과**: …`.
4. **모델 입력**(시스템 지시·툴 선언·턴 리마인더·툴 결과 문구·요약/추출 지시)이나 **모델 행동 가드**를 바꾸면: 실험실 실측 → 회귀 세트 전체 → 기준 대비 "새로 깨진 것"을 한 건씩 읽고 판정 → CHANGELOG 에 차이 기록. 오버헤드가 바뀌면 `TokenBudgetInvariantTest.MEASURED_OVERHEAD` 갱신(§3).
5. **회차 끝**: CHANGELOG 항목, 계획서 상태 `완료 (CHANGELOG x.y.z)`, 로드맵 해당 절에 "(완료 — …)", 사용 안내 한·영(사용자가 보는 동작이 바뀐 경우), README 기능·한계 표, 결정이면 ADR(`docs/architecture.md` 끝에 `### ADR-0NN.` — 다음 번호는 032). 커밋 `docs: <버전> 마무리 — …`.
6. **푸시는 하지 않는다** — 사용자가 요청할 때만. 회차가 끝나면 사용자에게 한국어로 요약하고 다음 회차로 넘어가도 되는지 묻는다(§2 STOP).

## 2. STOP — 멈추고 사용자에게 한국어로 물어야 하는 지점
| 상황 | 물을 것 |
|---|---|
| 휴대폰이 필요한 단계 | "휴대폰을 연결하고 잠금을 풀어 KOSMOS 채팅 화면을 띄워 주세요" — `adb devices` 에 `R3CY10QFYME` 가 없거나 앞 화면이 앱이 아니면 아무것도 하지 않는다 |
| 기존 테스트 단언을 바꾸거나 지워야 할 때 | 대상 `파일:줄`, 무엇을 왜 — 확인 뒤에만(구현 결함을 가리려는 단언 수정은 금지) |
| 규칙을 바꿔야 하는 처방(예: 백그라운드 로드, 계획에 없는 새 툴·새 화면) | 무엇이 달라지고 어떻게 되돌리는지 사용자 관점으로 |
| 회귀 세트에서 기준 대비 새로 깨진 항목이 이번 변경이 닿는 입력일 때 | 같은 실행에서 바꾸기 전·후를 비교한 결과와 함께 "채택/버림" |
| 비용(지연·토큰)과 품질을 맞바꾸는 결정, 기능 축소 | 선택지 2~3개 + 추천 |
| 큰 파일 내려받기(모델 등), 사용자 데이터 읽기 | 무엇을 어디서 얼마나 — 허락 뒤에만 |
| 회차 끝·푸시 | 요약 보고 후 "다음 회차로 갈까요? / 푸시할까요?" |

결정 질문은 **코드가 아니라 "앱을 쓸 때 무엇이 달라지고, 되돌리려면 어떻게 하나"**로 묻는다(사용자는 구현을 AI 에 맡기고 포트폴리오·면접에서 설명할 수 있기를 원한다).

## 4. 함정 모음 (지난 회차에서 실제로 겪은 것)
- **셸에 한글·역슬래시를 넣지 않는다** — heredoc 안의 파이썬 문자열에서 `\n`·`\s` 가 깨졌다. 편집은 에디터 도구나 **파일로 쓴 파이썬 스크립트**로. `sed` 로 정규식을 고치면 역슬래시가 사라진다.
- 파일은 UTF-8(BOM 없음). Git 의 LF→CRLF 경고는 무시해도 된다.
- **확인 실험은 모델이 그 경로를 실제로 탔는지부터** — 가드를 시험하려면 모델이 그 툴을 불렀어야 한다(런너 로그 `turn done: … toolCalls=[…]`). 0.39.2 M4b 에서 이걸 안 봐 확인이 두 번 헛돌았고 원인 진단도 틀렸다.
- **흉내는 앱의 실제 출력 모양과 같아야 한다** — 회귀 세트의 검색 결과 흉내에 앱의 충돌 안내가 없어서 "방금 말한 값이 메모에 지는" 결함을 실기기까지 놓쳤다(0.39.3 M4c). 의심되면 실기기 활동 기록 원문을 본다.
- 모델은 **같은 질문에 대한 자기 앞 답을 되풀이**한다(0.39.3 M4d) — 실기기 확인에서 앞 대화에 틀린 답이 남아 있으면 결과가 오염된다. 확인할 때는 앞 답이 없는 항목을 쓰거나 그 영향을 기록한다.
- 표본이 작으면 오판한다 — 6건에서 1 대 3 으로 보인 차이가 24건에서 4 대 5 였다(0.39.2 M2). 차이가 작으면 표본을 늘린다.
- 실기기에서 **답 직후 미리 만들기(0.39.2)는 몇 초 뒤에 끝난다** — 로그를 너무 빨리 읽으면 다음 턴 기록에 찍힌다(`session.py --wait=8`).
- 휴대폰 화면이 꺼지면(`mWakefulness=Dozing`, 앞 화면 NotificationShade) 도우미가 멈춘다 — 사용자에게 잠금 해제를 부탁한다. adb 서버가 새로 뜨면 USB 디버깅 허용을 다시 물을 수 있다.
- 새 테스트가 단독으로는 통과하고 전체 게이트에서 실패하면 실제 코드의 경쟁 조건을 의심한다(0.39.2 M3 — 취소 확인 누락을 찾았다). mockk 의 suspend 응답은 스레드를 막고 기다린다.
- `org.json` 을 쓰는 코드의 JVM 테스트는 Robolectric 러너가 필요하다.
- Kotlin AAR 의 파라미터 이름은 javap 로 확인(`maxOutputToken` — 단수였다).

- **M2 엔진 준비 직후 대화 미리 만들기** — Ready 를 받는 곳(예: `ConversationPrewarmer` 가 `ModelRunner.loadState` 를 구독하는 `start()` — init 구독 금지, AGENTS §2-④, `KosmosApp.onCreate` 에서 호출)에서
  현재 대화방(`SessionStore` 의 `active_session_id`)으로 `afterTurn(sessionId)` 와 같은 준비를 한다. 요약 catch-up(60초 조용한 뒤)·아침 브리핑과의 순서: 미리 만들기가 먼저, 다른 부수 추론은 그 뒤.
  사용자가 준비 중에 질문하면 남은 시간만 기다린다(0.39.2 와 같음). 테스트: Ready 에서 준비가 한 번 불린다 · Ready 가 반복돼도(복귀) 매번 · 새 요청이 오면 엔진에 닿기 전 준비는 취소.
- **M3 복귀 재로드** — M0 에서 "엔진 준비" 자체(약 8초)가 대부분이면 §2-⑥ 안에서 할 수 있는 것이 없다 → 닫고 기록(바꾸려면 STOP). 첫 답 몫은 M2 가 덮는다.
- **M4 실기기 확인** — M0 과 같은 시나리오로 전·후(첫 실행 첫 글자, 복귀 첫 글자, 드레인 중 질문 대기). 평소 턴 0.7~1.9초가 나빠지지 않았는지.
- **M5 마무리** — §1-5. 사용 안내에 체감 변화가 있으면 한 줄(한·영).

### 5.2 0.39.5 — 음성 인식 비교 (이득이 있을 때만 진행)
**목표**: 음성 입력의 전사 시간·정확도를 재고, 지금 Gemma 전사보다 확실히 나은 대안이 있을 때만 바꾼다.
**미리 정한 결정**: M0 결과로 "진행/닫기". 닫으면 결과만 기록하고 0.39.6 으로.
- **M0 녹음 세트 — STOP(사용자 몫)**: 사용자에게 한국어 발화 20~30개 녹음을 부탁한다 — 길이 5·10·25초, 조용한 곳·소음 있는 곳, 숫자·이름·날짜가 든 문장(예: "내일 오후 3시에 치과 예약 잡아줘").
  형식: 16kHz 모노 WAV(휴대폰 녹음 앱 파일이면 변환), 문장마다 정답 텍스트를 `scratch/lab/voice/truth.tsv`(파일명\t정답)로. **녹음과 정답은 커밋하지 않는다**(`.gitignore` 에 `scratch/lab/voice/` 추가).
- **M1 지금 전사 실측** — PC: `litert_lm` 으로 앱과 같은 오디오 전사(지시 없이 오디오만 — `GemmaModelRunner.generateWithAudio` 의 [WHY]) 시간·CER. 실기기: 앱에서 같은 파일로 전사 시간(임시 로그로 `TranscribeAudioUseCase` 전후).
- **M2 대안 비교(PC)** — whisper.cpp 모델(small·turbo 등) **내려받기 전 STOP**(크기·출처). 같은 녹음으로 CER·시간.
- **진행 조건**: 사용자가 느낄 이득(지연 절반 이하 또는 CER 뚜렷한 개선). 진행 시 별도 계획(모델 내려받기 `ModelDownloadService` 확장, 실패·미설치 시 Gemma 폴백, 16KB 페이지·x86_64 빌드, Gemma 와 동시 메모리) — 새 ADR, 화면이 바뀌면 STOP.

### 5.3 0.39.6 — 기억 검색 보강 (의미 검색 실측 · 결과 잡음)
**목표**: 유의어·상위 개념 질문("내가 좋아하는 음료가 뭐지?" ↔ 메모 "커피보다 녹차를 선호함")을 지금 검색이 얼마나 놓치는지 재고, 가벼운 것부터 보강한다. 0.39.3 에서 본 결과 잡음도 고친다.
- **M0 질의 세트(JVM, 결정적)** — 16~24쌍 + 표현 변형. `SearchMemoryToolExecutor` 를 메모리 안 저장소로 돌리는 테스트(예: `MemoryPipelineIntegrationTest` 전례)로 쌍마다 정답 메모가 결과에 있는지(적중률). 테스트로 커밋해 이후 보강의 기준으로.
- **M1 결과 잡음** — 실기기 원문(0.39.3 M4c): `- (과거 대화) 2건에는 다른 값이 적혀 있습니다: 5, 214, 6043, 1122, 9087)` — 질문(자전거 비밀번호)과 무관한 숫자.
  `RecallConflict`(`otherValues`·`contradicts`)가 요약 전체의 숫자를 긁는지 확인하고, 질의 낱말 근처의 값만 남기는 쪽으로. 툴 결과 문구가 바뀌므로 실험실 + 회귀 세트(newval·repeat·overlap 우선, 마지막에 전체).
- **M2 쓰기 시점 태그 보강** — 메모·에피소드 요약의 태그에 상위 개념을 더한다(요약·추출 지시 = 모델 입력 → 실측 선행). M0 세트로 전·후 적중률.
- **M3 읽기 시점 질의 확장** — 검색마다 +1~2초(exp37). **비용 결정이라 STOP**(M2 결과와 함께 선택지 제시).
- 한국어 임베더(C3)는 이 회차에서 하지 않는다 — 부족이 기록되면 새 ADR 과 함께 별도 회차(STOP).

### 5.4 0.4x — 문서 검색 → **STOP (제품 정의가 먼저)**
시작하지 않는다. 사용자에게 다음을 묻고 답을 계획서로 옮긴 뒤에만: ① 어디서 묻는가(채팅 첨부 / 문서 보관함 — 지금 문서 화면은 "AI 없이 가볍게 열어요") ② 어떤 문서를 얼마나(예: 50쪽+ 규정집) ③ 지금 "첨부해서 묻기"로는 왜 안 되는가.
답을 받으면 로드맵 0.4x 절(M0 실패 지점 실측 → 구조 인지 청킹 + 표 선형화 + 청크 단위 바이그램 → 부족할 때만 Kiwi·FTS5·임베딩)을 따른다.

### 5.5 작은 정리 (회차 사이에 끼워 넣기)
- **실기기 확인 목록 정리** — `docs/checklists/device_gate.md` 미완료 65개(완료 86)를 **닫을 것(이후 회차에서 이미 확인됨 — 근거 커밋·CHANGELOG 를 적는다) / 버릴 것(기능이 바뀌어 의미 없음) / 사용자 몫**으로 표로 나눈다.
  근거 없이 체크하지 않는다(AGENTS "허위 보고 금지"). 문서만 바뀌므로 게이트 없이 커밋.
- **CHANGELOG 형식** — 앞으로의 항목부터 결정·수치·경위를 찾기 쉽게(머리 한 줄 + [Changed]/[Fix]/[Note] 별 첫 문장에 결정, 수치는 괄호). 지난 항목은 고치지 않는다.
- **저장 데이터 보호 검토 — STOP(위협 모델은 사용자 결정)**: 메모에 비밀번호까지 저장되는데 DB·백업 암호화가 없다. 위협(앱 샌드박스 · 백업 파일 · 루팅·분실)별로 선택지(그대로 / SQLCipher / 백업 제외)와 대가를 문서로 정리해 보이고 결정받는다.
  화면 엿보기(어깨 너머)는 위협이 아니다(사용자 결정 — 부록 A).

### 5.6 하지 않는 것 (근거가 생기거나 사용자가 요청할 때만)
개인용 최적화 빌드(R8) · 8GB 기기(작은 모델 — 툴 호출 정확도 재측정이 필요한 큰 회차) · 실행 중 GPU 실패 시 CPU 폴백(실제 실패가 관측되면) · B2B 전환(제품 방향) · 턴 리마인더 축약(턴마다 −21토큰, ADR-017 위험 — 0.39.3 에서 사용자가 보류).

### commit-message-title-only.md

### litert-lm-python-api.md
LiteRT-LM 파이썬 패키지의 PyPI 이름은 **`litert-lm`** 이다 (`litertlm` 아님). import 는 `litert_lm`. conda `friday` 환경은 **0.18.0**(앱 AAR 과 같은 버전).

핵심 API:
- `Engine(model_path, backend=Backend.CPU, max_num_tokens=, max_num_images=, vision_backend=, audio_backend=, activation_data_type=ActivationDataType.FLOAT32, ...)` — 앱은 GPU·FP32 라 실측은 `backend=Backend.GPU, activation_data_type=FLOAT32` 로(kosmos_lab.create_engine 기본은 CPU) — `engine.tokenize(text)`/`detokenize` 로 실토큰 직접 측정 가능
- `engine.create_conversation(system_message=, messages=, tools=[함수들], automatic_tool_calling=False, thinking_config=, sampler_config=, constrained_decoding_config=ConstrainedDecodingConfig(enable=True))`
- `conversation.send_message(str | Message, max_output_tokens=…)` → Mapping. 툴 콜은 OpenAI 스타일: `{"tool_calls":[{"type":"function","function":{"name":...,"arguments":{...}}}]}`, 본문은 `{"content":[{"type":"text","text":...}]}`
- 툴 응답 주입: `Message.tool(Contents([Content.ToolResponse(name, result_json)]))`
- `conversation.token_count` 는 **프로퍼티**. 대화 생성 직후엔 0(히스토리는 첫 send 에서 프리필 — exp66b), send 후 실측값

`conda run` 은 여러 줄 `-c` 인자를 못 받으므로 `%USERPROFILE%\miniforge3\envs\friday\python.exe` 를 직접 호출할 것. 파이썬 stdout 은 리다이렉트 시 버퍼링된다 — `print(..., flush=True)`.

### no-shoulder-surfing-threat.md

### scratch-lab-is-disposable.md
`scratch/lab/` 의 파이썬 하네스는 **실기기 테스트 횟수를 줄이려고** 만든 도구다. 스크립트(`scratch/lab/*.py`)는 추적되고 실험 출력·자동 생성 픽스처는 `.gitignore` 대상이다(0.35.1). 그대로 복원할 필요는 없다 — 필요에 따라 그때그때 새로 구성해서 실험한다.

**Why:** 실험실의 가치는 "앱의 실경로와 같은 설정으로 PC 에서 재판정할 수 있다"는 점에 있다. 기록에 남은 실험 결과(CHANGELOG·ADR)는 신뢰해도 된다고 사용자가 확인했으므로 재현을 위해 다시 돌릴 이유가 없다(예외: 모델 회귀 세트 `scratch/lab/regression/run.py` 는 회차마다 다시 돈다 — AGENTS §2-⑤).

**How to apply:** 실험이 필요해지면 `scratch/lab/` 에 그 실험만을 위한 스크립트를 새로 짠다(`expNN_이름.py`, 맨 위 docstring 에 질문·조건·판정). 앱과 맞출 값은 `Constants.kt`·`buildEngineConfig`·`ConversationConfig`(greedy topK=1, ThinkingConfig off, 제약 디코딩)·`KosmosToolDeclarations` 에 있다. 프롬프트는 `PromptFixtureExportTest` 픽스처를 쓴다.

### test-assertion-rule-exception.md
AGENTS.md §2-② 의 "기존 테스트 단언 수정 0건" 규칙은 사용자가 예외를 허용했다(2026-09-30). 죽은 필드를 고정하는 단언, 공용 대역으로 옮기며 바뀌는 단언, 중복 테스트 통합 등.

**Why:** 규칙이 죽은 코드·중복 테스트 정리를 막고 있었다. 사용자는 정리를 원하지만 테스트가 몰래 약해지는 것은 원하지 않는다.

**How to apply:** 단언을 수정·삭제해야 하는 변경은 먼저 대상(파일:줄, 무엇을 왜)을 목록으로 보여주고 사용자 확인 후에만 적용한다. 구현 결함을 가리려고 단언을 고치는 것은 여전히 금지.

### user-goal-portfolio.md
KOSMOS 의 목표는 두 가지 — 실제로 쓸 앱, 그리고 **포트폴리오·면접에서 직접 설명하고 방어할 수 있는 프로젝트**(2026-10-27 사용자 언급). 구현은 거의 전적으로 AI 에이전트에 위임해 코드 디테일에는 의견을 내기 어렵다고 함.
