# 0.41.0 — 문서 보관함과 색인 (모델 추론 없음)

## Context
목표는 **사용자가 등록한 문서들(규정집·전공서적·법령)을 채팅에서 찾아 근거와 함께 답하는 것**이다. 기관·기업·학생 사용(사용자 결정, 2026-11-03).
두 회차로 나눈다 — 이 회차(0.41.0)는 등록·색인·검색 엔진까지, 모델 입력은 바꾸지 않는다. 0.41.1 이 채팅 툴(`search_documents`)·출처 표시를 붙인다.

**규모 기대치**: 최소 "전공서적 한 권"(300~600쪽, 50만~100만 자). 300~500자 조각이면 책 한 권 2천~3천 조각, 여러 권이면 1만+.
- 기억 검색의 인메모리 바이그램 전수 스캔(`BigramMatcher`, ADR-025 — 2,000건 17ms)은 이 규모에서 **메모리가 먼저 무너진다**(조각마다 바이그램 집합을
  들고 있어야 한다). ADR-025 의 규모 게이트(2,000건+)를 처음부터 넘는다 → DB 색인이 필요하다.
- 색인 후보: **(A) FTS4 + 바이그램 문자열** — 조각 글자를 `BigramMatcher.bigrams` 로 쪼개 공백으로 이은 문자열을 FTS4 가상 테이블에 넣고
  (`simple` 토크나이저가 공백으로 자른다), 질의 바이그램 `OR` 매치로 후보 수십 개를 뽑은 뒤 앱에서 `BigramMatcher.score` 로 다시 매긴다.
  FTS4 는 안드로이드 프레임워크 SQLite 에 늘 있고 Room `@Fts4` 가 있다(FTS5·한국어 토크나이저 문제를 피한다). 색인은 압축 포스팅 목록이라 작다.
  **(B) 바이그램 포스팅 테이블**(bigram, chunkId) — 단순하지만 책 한 권에 수십만 행.
  M0 에서 크기·질의 시간·회수율로 고른다.
- 채팅 쪽 회수율의 한계도 M0 에서 잰다: 바이그램은 바꿔 말한 질문("늦게 납품한 벌금" ↔ "지체상금")을 놓친다. 이 회차는 어휘 검색까지이고,
  부족하면 형태소(Kiwi)·임베딩 비교는 후속(로드맵 원안).

## 결정 (사용자, 2026-11-03)
- 묻는 곳 = **채팅**. 문서 화면 검색창은 두지 않는다(대화·기억이 흩어진다).
- 보관함 범위 = **사용자가 직접 등록한 문서만**. 최근 문서 전체·폴더 전체는 범위가 커서 작은 모델 결과가 나빠진다.
- D1 = **새 툴 `search_documents`**(0.41.1) — 보관함이 비면 선언하지 않는다(위키 토글과 같은 게이트).
- D2 = **원본은 제자리**(지속 열람 권한만), 뽑은 글자·조각·색인만 DB. 원본이 사라져도 검색은 되고 원문 열기만 "원본을 찾을 수 없음".
- D3 = **문서 화면에 "보관함" 구역** — "+" 등록, 뷰어 메뉴 "보관함에 추가", 목록에서 삭제·다시 색인.

#### M0 후속 — 모델 검색어·dense 임베딩 (0.41.1 사전 실측, 2026-11-03)
