# 0.39.1 — 지연 개선 1: 요약은 조용해진 뒤에 · 부수 추론 뒤 3.5초의 원인

## 목표
0.39.0 M1 실측에서 보인 체감 지연 중 **보정 장치와 무관한 둘**을 고친다. 재생성 비용(+6초)은 장치를 건드리므로 0.39.2(보정 장치 정리) 뒤로.
1. 에피소드가 닫힌 직후의 질문이 요약 추론에 막힌다 — 대기 11.9초 + 대화 준비 3.5초 = 첫 글자 17.1초(평소 0.7~1.9초).
2. 부수 추론(oneShot) 뒤 첫 채팅 턴은 재생성 로그 없이 대화 준비가 3.3~3.5초 — 두 번 관찰, 원인 모름.

## 정한 것 (2026-10-29 사용자)
1. **요약은 마지막 대화 턴이 끝나고 60초 조용하면 시작** — 그 사이 새 질문이 오면 다시 센다. 기다리는 중에 앱을 나가면(엔진 해제) 다음 실행 때 같은 규칙으로.
   요약이 이미 도는 중에 보낸 질문은 여전히 기다린다(선점 취소는 하지 않는다 — 0.38.6 취소 결함과 같은 경로).
2. **앱 시작 직후(엔진 Ready) 밀린 요약도 같은 규칙** — Ready 에서 바로 돌리지 않고 조용해진 뒤. 아침 브리핑은 열자마자 보여 주는 것이라 그대로.

## 지금 알고 있는 것
- `EpisodeSummarizeScheduler`: 경계에서 닫힌 에피소드를 큐에 넣고, ① 턴 종료(`AssistantOrchestrator` 가 `onTurnCompleted()`) ② 엔진 Ready(catch-up + drain)에서 바로 비운다.
  드레인은 `BackgroundInferenceGate` 뮤텍스로 수동 기억 정리와 직렬화, 발열 게이트로 미룰 수 있다. 요약 뒤 자동 추출(oneShot 하나 더)이 이어진다.
- 엔진은 한 번에 하나만 추론한다(`llmDispatcher` 단일 스레드 + 뮤텍스) — 요약이 도는 동안 채팅 턴은 기다린다.
- 재사용 판정(`decideConversation`)은 캐시된 채팅 대화의 `getTokenCount()`(네이티브)를 부른다 — 3.5초가 여기서 나는지, 엔진이 부수 대화 뒤 채팅 대화 상태를 다시 올리는 비용인지 모른다.

## 마일스톤 (각각: 게이트 → 커밋)
- **M0 3.5초 원인 (실험실, 코드 수정 0)** — PC 에서 앱과 같은 순서를 재현: 채팅 대화로 몇 턴 → 부수 대화 생성·추론·닫기 → 채팅 대화의 토큰 수 조회 시간 · 다음 턴 첫 글자 시간.
  부수 대화 없이 같은 것을 대조. 원인이 판정 쪽(토큰 수 조회)이면 M2 에서 피하고, 엔진 쪽이면 기록하고 0.39.2 이후 후보로.
- **M1 조용해진 뒤 요약** — 스케줄러가 바로 비우지 않고 "마지막 턴 종료 후 60초 무활동"을 기다린다(새 요청이 오면 다시 센다). Ready catch-up 도 같은 대기 뒤.
  시각 판정은 주입 가능한 시계·지연으로(AGENTS §2-④), 테스트: 60초 전 질문이 오면 미뤄짐 · 조용하면 실행 · Ready 직후 바로 돌지 않음 · 앱 해제 시 다음 Ready 로.
  기존 스케줄러 테스트가 "턴 종료 즉시 드레인"을 단언하면 사용자 확인 후 바꾼다(§2-②).
- **M2 3.5초 대응 (M0 결과에 따라)** — 판정 쪽이면 토큰 수 조회를 피하는 방식(예: 앱이 센 값 재사용)으로. 엔진 쪽이면 바꾸지 않고 기록.
- **M3 실기기 확인** — 0.39.0 M1 의 긴 메시지 시나리오로 경계 직후 질문의 첫 글자 시간(전 17.1초), 60초 뒤 요약이 실제로 도는지, 부수 추론 뒤 턴. `scratch/lab/device/`.
- **M4 마무리** — CHANGELOG, 계획서 상태, 로드맵.
