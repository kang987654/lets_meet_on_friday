# 0.41.4 — 활동 기록(감사 로그) 해시 체인과 기록 순서 결함 수정

## Context
활동 기록(`audit_log`)은 비서가 한 일(모델 실행·툴 실행·승인/거절·검색·백업·발열)을 남긴다(설정 › 활동 기록). 기록 경로는 `AuditTrailService` → `AuditRepository.save` 한 곳이다.
지금은 행마다 독립이라 **행을 지우거나 고치거나 끼워 넣어도 흔적이 남지 않는다.** 이 회차는 행을 앞 행의 해시로 잇는 체인을 붙이고, 코드 대조로 확인한 기록 순서 결함 3건을 고친다.

### argon 계획서 대조 (AGENTS §2-① — 외부 분석은 먼저 대조)
- **사실 — 결함 3건 모두 지금 코드에 있다**:
  1. 조회 정렬이 `timestamp` 하나(`AuditDao.getEvents`) — 같은 밀리초의 두 기록(승인 직후 툴 실행)은 순서가 정해지지 않는다. 체인을 붙이면 순서가 곧 검증 대상이라 단조 증가 번호가 필요하다.
  2. 내보내기(`ExportMemoryUseCase`)가 ZIP 을 만든 **뒤** 기록 — 내보낸 백업 안에는 그 내보내기 기록이 없다.
  3. 복원(`ImportMemoryUseCase`)이 DB 파일을 바꿔치기한 **뒤** 열린 Room 연결로 "복원 성공"을 쓴다(`ExportImportManager.restoreFromZip` 은 재시작 전제로 DB 를 닫지 않는다) — SQLite 는 열린 파일 바꿔치기 뒤의 쓰기를 보장하지 않는다(그 기록은 사라지거나 새 파일의 WAL 과 엉킬 수 있다).
- **낡음**: DB 버전(argon 은 v10→11, 지금은 **v13→v14**), `MEASURED_OVERHEAD` 수치, 게이트 명령(`verifyRoborazziDebug` 는 `test` 가 이미 기준 이미지 비교).
- **빠진 것 — 위협 모델**: argon 판(안 A, 키 없는 SHA-256 체인)은 **DB 를 고칠 수 있는 사람이 체인을 처음부터 다시 계산하면 감지하지 못한다.** 키 없는 체인이 잡는 것은 "체인을 모르는 편집"(행 하나 지우기·고치기, 도구로 대충 손댄 백업)과 우연한 손상·순서 꼬임이다.
  면접에서 반드시 나오는 질문이라 무엇을 막고 무엇을 못 막는지 정하고 이름도 그에 맞게 붙인다(아래 Q1).
- 기기 위협 배경(ADR-032): 앱 DB 는 안드로이드 샌드박스·FBE·자동 백업 차단으로 보호된다 — 앱 밖에서 DB 를 고칠 수 있는 길은 루팅 기기와 **사용자가 직접 내보낸 백업 ZIP**(편집 후 다시 가져오기)뿐이다.

## 고정 제약
- 모델 입력·토큰 예산 불변(프롬프트·툴 표면 무관) — 회귀 세트 불필요.
- 기존 테스트 단언 불변. 화면 기준 이미지는 체인이 정상일 때 그대로(경고는 이상할 때만).
- 기록 저장은 지금처럼 실패해도 앱 동작을 막지 않는다(감사 기록 실패가 채팅을 막으면 안 된다).
- 해시 계산은 순수 JDK `MessageDigest`(의존성 0).

## 결정 (사용자, 2026-11-05)
- **Q1 = 키 없는 SHA-256 체인 + 활동 기록 화면 끝에 "지금 체인 머리" 한 줄** — 개인용이라 실제 위협은 파일 손상·버그(누락·순서 꼬임)이고, 체인을 다시 계산하는 악의적 편집은 **범위 밖으로 문서에 명시**한다(이름도 "무결성 증명"이 아니라 "변경 감지"). 백업 파일·내보내기 화면은 바꾸지 않는다. 체인 머리 한 줄은 "적어 두면 재계산도 드러난다"는 확장의 맛보기.
- **Q2 = 체인 시작 전으로 표시** — 지금 휴대폰 기록은 테스트용이라 업데이트 뒤 대화 초기화로 정리한다(사용자). 표시 자체는 옛 백업(v12·v13)을 복원할 때를 위해 필요하다(새 열의 기본값이라 비용 0).
- **Q3 = (a)** 대화 초기화로 활동 기록을 지우면 새 체인의 첫 기록으로 `RESET` 사건을 남긴다.
- **Q4 = 이상할 때만 경고** — 정상이면 지금 화면 그대로, 깨졌으면 목록 위 경고 띠, "원문 보기"에 `#번호 · 지문 앞뒤 8자 · 앞 지문`, 화면 끝에 체인 머리 한 줄.

## 계획 단계에서 정할 것 (사용자 확인)
- **Q1. 체인 방식 (위협 모델)**
  - (a) **키 없는 SHA-256 체인**(argon 안 A) — 백업을 다른 기기에 복원해도 검증된다. 막는 것: 체인을 모르는 편집·손상·순서 꼬임. 못 막는 것: 체인을 다시 계산하는 사람. 이름은 "무결성 증명"이 아니라 **"변경 감지(tamper-evident)"**.
  - (b) **Keystore 키 HMAC 체인** — 키가 기기 밖으로 나가지 않아 다시 계산해도 들킨다. 대가: 다른 기기에 복원한 백업·앱 재설치 뒤(키 삭제) 옛 구간은 "이 기기에서 검증할 수 없음"으로만 보인다.
  - (c) **추천: (a) + 머리 해시 고정점** — 체인은 (a), 백업 내보내기 때 **그 시점 체인 머리 해시와 번호를 manifest 와 화면에 남긴다**(사용자가 다른 곳에 적어 두거나 공유한 값과 대조하면 "그 이후 다시 계산"까지 드러난다). 복원 호환을 지키면서, "다시 계산하면?"에 "고정점과 대조한다"로 답할 수 있다. 머리 해시는 활동 기록 화면에서도 볼 수 있게 한다.
- **Q2. 기존 기록** — (a) **추천: 체인 시작 전 기록으로 표시**(번호 0, 검증 대상 아님 — 화면에 "체인 시작 전" 한 줄) — 보호받지 않던 기록을 보호받은 것처럼 보이지 않게. (b) 마이그레이션 때 기존 행을 시각순으로 다시 이어 체인에 넣는다(전부 검증 대상이 되지만, 그 시점 이전 변조는 이미 알 수 없다).
- **Q3. 대화 초기화(활동 기록도 지움)** — 지금 `ResetTarget.CONVERSATIONS` 가 `audit_log` 를 통째로 지운다. (a) **추천: 지운 직후 새 체인의 첫 기록으로 "초기화" 사건을 남긴다**(기록이 비어 있는 이유가 체인 안에 있다 — 새 사건 종류 `RESET`). (b) 그대로(빈 체인에서 새로 시작).
- **Q4. 화면** — 체인이 정상이면 지금 화면 그대로, 이상이면 목록 위에 경고 띠(argon 안). 펼친 항목의 "원문 보기"에 `#번호 · 해시 앞뒤 8자 · 앞 해시`. 여기에 (c) 고정점을 고르면 화면 맨 아래(또는 메뉴)에 "지금 체인 머리" 한 줄을 더한다 — 확인 부탁.

## 마일스톤

### M1 — 도메인 (`:domain`, 순수 JVM)
- `AuditEvent` 에 `chainSeq: Long = 0`, `prevHash: String = ""`, `entryHash: String = ""`(기본값 — 기존 호출부·테스트 무수정).
- `AuditHashChain`: `GENESIS`, `LEGACY` 표지, `entryHash(seq, prev, id, timestamp, type, sessionId, details)` = SHA-256 hex(필드 구분자·길이 접두로 경계 모호성 제거 — `"a|b"+"c"` 와 `"a"+"b|c"` 가 같은 바이트가 되지 않게),
  `verify(오름차순 사건)` → `Valid(검증 수, 체인 전 수, 머리 해시)` / `Tampered(번호, 사건 id, 이유: HASH_MISMATCH · LINK_BROKEN · SEQUENCE_GAP)`. 여러 쪽으로 나눠 이어 검증할 수 있게(누적 상태를 넘기는 형태 — 기록이 수만 건이어도 한 번에 메모리에 올리지 않는다).
- `ExportMemoryUseCase`: 내보내기 **시작** 기록을 ZIP 만들기 전에 남기고(백업 안 체인에 포함), 실패면 실패 기록을 더한다.
- `ImportMemoryUseCase`: 성공이면 열린 연결에 쓰지 않는다(재시작 뒤 첫 기록은 복원된 체인에 이어짐), 실패만 기록. (Q3 와 같은 결: 복원 성공 사실은 재시작 뒤 앱이 "복원 직후" 표지를 보고 새 체인에 남기는 안도 검토 — 복잡하면 빼고 CHANGELOG 에.)
- 테스트: 이어 쓰기 → 통과, 가운데 한 글자 변조 → HASH_MISMATCH, 행 삭제 → SEQUENCE_GAP/LINK_BROKEN, 순서 바꿈, 체인 전 행 건너뛰기, 쪽 나눔 검증 = 한 번에 검증, 경계 모호성.

### M2 — 저장 (`:data`, Room v13 → v14)
- `audit_log` 에 `chainSeq INTEGER NOT NULL DEFAULT 0`, `prevHash TEXT NOT NULL DEFAULT 'LEGACY'`, `entryHash TEXT NOT NULL DEFAULT ''` + `chainSeq` 색인. (Q2 = (b) 면 마이그레이션에서 기존 행을 시각순으로 이어 계산.)
- 저장은 **한 트랜잭션**: 머리 조회 → 다음 번호·앞 해시 → 해시 계산 → 삽입. 동시 저장(코루틴 여럿)도 Room 트랜잭션이 한 줄로 세운다 — 같은 밀리초 연속 저장 테스트.
- 조회 정렬 `ORDER BY chainSeq DESC, timestamp DESC`(체인 전 행은 기존처럼 시각순 뒤에). 검증용 오름차순 쪽 조회.
- Q3 = (a) 면 데이터 초기화가 `audit_log` 를 지운 같은 트랜잭션에서 `RESET` 첫 기록을 남긴다(`AuditEventType` 추가 — 활동 기록 라벨·아이콘·한영 문자열).
- 테스트: 마이그레이션 DDL(14.json 대조)·기존 행 보존, 이어 쓰기·변조 감지(실제 Room), 동시 저장, 초기화 뒤 첫 기록.

### M3 — 화면 (`:app`)
- `AuditViewModel`: 화면에 들어오면 쪽 단위로 검증(IO, 화면을 막지 않음) → 상태(검증 중 / 정상 n건 · 체인 전 m건 · 머리 / 이상 — 번호·이유).
- `AuditScreen`: 이상이면 목록 위 경고 띠(무엇이 어디서 깨졌는지 한 줄), "원문 보기"에 체인 정보 줄, 목록 끝에 "지금 체인 머리" 한 줄(Q1).
- 화면 카탈로그: 경고 띠·원문 체인 줄 장면 추가(정상 화면 기존 이미지는 그대로).
- 테스트: 정상/이상 상태, 쪽 나눔 검증 중 화면 상태.

### M4 — 문서·실기기
- 실기기: 실제 기록이 든 DB v13 → v14, 활동 기록 원문의 체인 줄, 백업 내보내기 → ZIP 안 체인에 내보내기 기록, (가능하면) 내보낸 DB 한 행을 고쳐 가져와 경고 띠 확인, 검증 시간(기록 수천 건).
