# 0.42.8 임베딩 엔진 기본값을 CPU 로

> **상태**: 계획 (승인 대기).
> 정본 순서: **AGENTS.md > 이 계획서**.
> 근거: 2026-11-18 휴대폰 확인(0.42.7 설치 뒤, SM-S938N). 회차 성격: 휴대폰에서 찾은 것(버전 규칙 끝 숫자).

## 휴대폰에서 본 것 (로그, `adb logcat` PC 로만 — 등급 1, 표본 작음)
| 순서 | 임베딩 엔진 | 결과 |
|---|---|---|
| 14:52 새로 설치 뒤 첫 실행 — 시작 oneShot(정상, 144토큰) 1초 뒤 임베딩 GPU 로드 | GPU | 채팅 두 턴 모두 깨진 글자 약 3,000자 → KV 4,096 초과, 툴 호출 0 |
| 15:06 같은 프로세스에서 "안녕"(대화는 예산 초과로 새로 만든 뒤) | GPU | 깨짐 — 프로세스 안에서 이어진다 |
| 15:07 강제 종료 → 다시 켜기 | GPU | 두 턴 모두 깨짐 |
| 15:12 `debug_embed.txt` = CPU → 강제 종료 → 다시 켜기 | CPU | 두 턴 정상(일정 승인 시트 · "어떤 날짜에…?" 되묻기) |

- 0.42.4(11-17)와 같은 방향: GPU 3/3 깨짐, CPU 정상. 이번에는 **채팅 답 자체**가 깨졌다(0.42.4 는 채팅 밖 추론만) — 실사용에 바로 걸린다.
- 11-18 오전에는 같은 조건에서 재현되지 않았다(0/3) — GPU 임베딩은 충분조건이 아니지만, CPU 로 두면 두 번 모두 사라졌다. 근본 원인(런타임·드라이버의 두 엔진 공존)은 앱에서 고칠 수 없다.
- 디버그 파일은 확인 뒤 지웠고 GPU 로 되돌렸다. 깨진 답 5개는 채팅 기록에 남아 있다(앱 데이터라 손대지 않음).

## 대가 (기록된 실측, 다시 재지 않음)
- 조각당 GPU FP32 **75ms** vs CPU **83ms**(0.41.7 보충 — ADR 의 43ms 는 예전 FP16 수치). 민법 1,136조각 기준 약 +9초.
- 검색 품질: exp83 @1 GPU FP32 64 · CPU 63, 코사인 평균 0.9995 — 사실상 같다.
- 엔진 로드는 CPU 가 더 빠르다(이번 로그 407ms vs GPU 936~1,087ms). GPU 메모리도 덜 쓴다.

## 결정 (승인 때 정할 것)
- **D1 처방** — (가) **기본값 CPU (추천)**: 한 줄 바꾸기, 대가 위와 같이 작다. GPU 는 디버그 파일로만(다시 갈라 볼 때).
  (나) 대량 벡터 만들기(문서 등록)만 GPU 로 하고 끝나면 내리기 — 내린 뒤에도 깨짐이 이어지는지 모르고(이번에 프로세스 안에서 이어졌다) 휴대폰 실측이 더 필요하다. 이득은 조각당 8ms.
- **D2 이미 만든 벡터** — **다시 만들지 않는다 (추천)**: 코사인 0.9995 라 GPU 로 만든 메모·문서 벡터를 CPU 질의와 그대로 쓴다. 모델 표지(`embeddinggemma-2-740m-fp32`)는 그대로.
- **D3 채팅 답 깨짐 안전장치** — **이번엔 하지 않고 기록만 (추천)**: 0.42.4 의 `BrokenOutput`(한글 비율 30%)을 채팅 스트림에 걸면 깨진 답을 일찍 멈출 수 있지만, 영어 사용자·코드 답에서 오탐 위험이 있고 원인을 막으면 필요가 줄어든다. 다른 원인으로 다시 보이면 그때.

## 고정 제약
- 채팅 모델 입력 불변 → 회귀 세트·`MEASURED_OVERHEAD` 대상 아님.
- GPU 실패 시 CPU 로 한 번 더 여는 폴백(`openWithFallback`)은 시작 백엔드만 바뀐다 — CPU 가 기본이면 CPU 하나만 시도.
- 기존 테스트 단언 불변(`EmbeddingBackendTest` 는 `DEFAULT` 를 기호로 비교 — 값이 바뀌어도 그대로 통과할 것으로 본다. 깨지면 대상을 먼저 보여 준다).
- 휴대폰 확인은 짧게(약 5분, 미리 묻기): 강제 종료 → 켜기 → 채팅 두 턴 정상 · 로그 `backend=CPU`. 디버그 파일 없음.
