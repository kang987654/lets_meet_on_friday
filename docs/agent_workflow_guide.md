> **관련 모듈**: 프로젝트 전 영역 (개발 프로세스 지침)

## 핵심 원칙
- **한 세션에서 계획 → 구현 → 실기기 확인까지 잇는다.** 대화가 길어지면 요약(컨텍스트 압축)이 일어나므로, 이어 가는 데 필요한
  것은 **저장소 파일**에 둔다 — 회차 계획서(`docs/plans/<버전>-<회차>.md`, 구현 전에 커밋), CHANGELOG, ADR. 지침의 정본은 루트 `AGENTS.md` 하나다.
- **사람은 판단·우선순위·합격 기준·실기기 사용을 맡는다.** 결정은 코드가 아니라 "쓸 때 무엇이 달라지고, 되돌리려면 어떻게 하나"로
  받는다. 기존 테스트 단언 변경도 "그 테스트가 지키던 동작과 바뀐 뒤의 동작"으로 받는다.
- **같은 에이전트가 짜고·테스트하고·기록하고·평가한다는 약점**을 아래 두 장치로 메운다.

## 회차 흐름
1. **계획** — "0.x.y 계획 세워줘". 탐색(코드 수정 없음) → 결정 질문 → 마일스톤·게이트. 승인되면 계획서를 커밋한다.
   모델 입력(툴 선언·지시·리마인더·툴 결과 문구)을 바꾸는 회차는 M0 실측이 계획에 들어간다(`AGENTS.md` §2-⑤).
2. **구현** — "M1 진행해줘". 마일스톤마다 `./gradlew test lintDebug assembleDebug` 녹색 → 한 줄 제목 커밋.
   계획과 갈리면 `[WHY]` 주석과 CHANGELOG, 계획서 결과 줄에 적는다.
3. **실기기 확인** — 마지막 마일스톤. `docs/checklists/device_gate.md` 에 절을 남기고, 사람만 볼 수 있는 항목은 그렇게 표시한다.
4. **푸시** — 사람이 요청할 때만.

## 빈틈을 메우는 두 장치
- **독립 리뷰** — 회차 끝이나 큰 변경 뒤, 작업한 세션과 별개로(새 세션·다른 모델·`/code-review`) 돌린다.
  리뷰어에게는 **결론이 아니라 코드·변경분**(`git diff <계획 커밋>..HEAD`)을 준다 — 요약을 주면 그 결론을 따라간다.
- **외부 분석 대조** — 다른 모델·도구가 낸 검토·기획을 받으면 계획에 옮기기 전에 두 가지를 묻는다:
  "기준 버전이 지금과 같은가", "수치마다 근거가 공식 문서 / 우리 실측 / 추정 중 무엇인가"(`.agents/04_MODEL_EVIDENCE.md`).
  2026-10-27 의 외부 보고서는 0.38.5 기준 낡은 수치와 외부 추정치를 우리 기기 사실처럼 처방에 옮겼다.
